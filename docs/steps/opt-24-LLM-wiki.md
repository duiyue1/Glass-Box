# 优化 24 · LLM wiki（第一层：生成 + 校验 + 知识页）

资料库到现在为止是「原文 → 检索 → 一次性答案（用完丢掉）」，每次提问都要重新在原文里翻。
wiki 是在原文之上加一层：**把结论整理成条目，持久保存**，跨文档的冲突在编译时就标出来。

方案是照 GitHub 上几个高星项目改的，不是我自己拍的：

- **Tencent/WeKnora（19.9k★）Wiki Mode + issue #919**：页面分类（`source/concept/entity/analysis`
  + `index.md` / `overview.md` / `AGENTS`（Schema Config）/ `log.md`）、三个核心操作
  （Ingest / Query / Lint）、以及那句点题的对比——标准 RAG 的答案用完就丢，wiki 是**复利知识**。
- **AsyncFuncAI/deepwiki-open（17.6k★）**：先让模型定 wiki 结构、再逐页生成。
  更重要的是抄它**公开承认的缺陷**：每页独立生成导致跨页内容大量重复。
- **Wiki.js（25k★）/ siyuan（45.8k★）/ Trilium（28k★）**：Git-backed 纯 Markdown、local-first、
  `[[wikilink]]` + 反向链接。
- 一个**品类空白**（2026 年多份横评都提到）：BookStack / Wiki.js / Outline
  **都不知道一篇文章什么时候不再成立**——没有过期标记，也没有「原文变了 → 哪些页面失效」的联系。
  这恰好是我们能补上的地方。

## 落盘：就是普通 Markdown 文件

```
.glassbox/kb/wiki/
  AGENTS.md          生成规则（首次生成从 src/kb/AGENTS.default.md 复制，之后只读你那份）
  index.md           分类目录（也是将来注入给模型的那一份）
  log.md             操作日志，只追加
  source/<slug>.md   一篇原文一页（导航用，不搬数字）
  concept/<slug>.md  一个机制/约定一页（真正用来回答问题的）
```

不进 `index.json`，因为条目是**人要读、要改**的东西。纯文件意味着能用编辑器直接改、能 git 管、能 grep
——Wiki.js 的核心卖点，我们零成本就拿到了。

frontmatter 里除了 title/summary/aliases/sources，有两个字段是这一层的关键：

- `sourceHash` —— 依据块内容的哈希。**原文一改 → 哈希不一致 → 条目自动算 stale**，面板上黄点提示重建。
  这就是上面说的那个品类空白。
- `verified` / `unverified` —— 溯源校验结果。

## 生成管线：三步，只有前两步调模型

**1. 结构阶段**（`normalizePlan`）：只看标题树 + 每块首句（不看全文，省 token），
让模型决定拆成哪几页，并把**原文块互斥分配**给页面。

模型经常无视互斥规则，所以代码里强制执行：同一个块被多页抢时**先到先得**，
一个块都抢不到的 concept 页直接丢弃，模型没给 `source` 页就补一个，越界块号丢掉，
非法 ref 用标题重造。

**互斥分配是冲着 deepwiki-open 那个缺陷去的**：它每页各自去检索上下文，结果跨页大量重复。
在我们这儿重复的代价更直接——重复条目会在检索时互相挤占那 800 token 的注入预算。
块的归属在结构阶段定死，编译时模型只看得到自己那份。

**2. 编译阶段**（`compilePage`）：把 `AGENTS.md` 当 system prompt，只喂给它分到的块
（每块带 `【文档id#块号】` 标注），要求结论先行、每条带数字的结论必须写出处。

`source` 页看全篇但按头 70% + 尾 30% 截到 6000 字——它写的是导航，不需要读完全文。

**3. 校验阶段**（`verifyBody`，不调模型）：条目里出现的每个数字和标识符，
必须能在**它自己声明的依据块**里一字不差地找到，找不到就 `verified: false` 并把缺的字面记下来。

几个细节是踩过坑之后定的：

- 比较时两边都去空白：条目写「30秒」、原文写「30 秒」不算编造
- 标识符大小写不敏感：`setnx` vs `SETNX` 是排版差异，不是编造
- **数字两侧都卡边界**：原文有「100」不能让条目里的「10」蒙过去。
  这是 opt-22 在评测指标上踩过的同一个坑，这次直接写成了单测
- 校验用的原文以 `page.sources` 为准、从 KbStore 现取 —— 模型没法靠「少报来源」绕过校验
- 纯中文词不校验：同义改写在中文里太常见，卡它会全军覆没；数字和标识符改一个字就是错，卡这两类性价比最高

WeKnora 和 deepwiki-open 都没有这一步。他们的 wiki 是平台产的、有人管；我们是自己让 LLM 编译原文，
**必须有一道机械闸门**，否则 wiki 就是个更精致的幻觉放大器。

另外两处「宁可失败也不要脏数据」：模型输出没有 frontmatter 一律判失败
（多半是在说「我做不到」这类话，写进条目比丢掉更糟）；`write()` 对非法 ref 直接抛错（挡路径穿越）。

## 真实模型跑出来才发现的五个问题（都已修）

单测全绿之后拿 GLM-5.2 在真实资料库上跑，第一次 8 页里 **3 页硬失败、2 页误判未通过校验**。
下面每一条都是那几轮跑出来的，不是我想象的边界情况：

1. **`claimsOf` 把 Markdown 排版序号当成了声明**。一段「被否决的三个方案」用有序列表写，
   `1.` `2.` 被抽成内容数字送去校验，原文里没有独立的「2」，整页判未通过。
   修法：挖掉行首序号（`1. ` / `- 2) ` / `## 3. `）再抽字面。
2. **校验语料少给了文档标题和块标题路径**。`material` 里是 `【文档id#块号】[标题路径]` 原样给的模型，
   但校验只拿块正文比对——source 页写「软件设计文档（SDD）」，SDD 只在文档标题里，整页因此未通过。
   修法：校验语料 = 文档标题 + 各块标题路径 + 块正文；**哈希仍然只算块正文**，
   因为 `app.ts` 的 stale 判定是拿块正文重算的，两边口径必须一致。
3. **frontmatter 解析器只认行内写法**。模型时不时改用块状列表和折叠标量
   （`aliases:` 换行 `  - x`、`summary: >` 续行），结果 `summary` / `aliases` 静默变空
   ——正文写得很好，摘要和别名全丢。修法：解析器补上这两种写法。
4. **依据只按 frontmatter 记账**。模型正文写了 `[调度服务-sdd#4]`、frontmatter 里忘了列 #4，
   于是校验语料缺 #4，那句「低于 95%」被判成编造。这是记账不一致，不是幻觉。
   修法：依据 = frontmatter 声明 ∪ 正文实际引用，**再与分配给它的块求交**。
   求交不能省——概念页引用一个没分给它的块（真抓到过：引 #7 写 NTP）是跨页泄漏，必须继续判未通过。
5. **source 页的 ref 让模型自己起**，于是三轮跑出 `调度服务 SDD` / `调度服务-SDD` / `调度服务SDD`
   三个孤儿摘要页——正是我们声称要避免的跨页重复。修法：source 页的 ref 由文档标题定死。

### 输出格式：三级容错 + 一次重发，仍然不能保证 100%

同一份提示词、同一份资料，模型每轮的输出形态都在变：这轮规规矩矩，
下轮 ```` ```yaml ```` 加 `body: |`，再下轮字段都对但一个 `---` 都不写，
再下轮直接从 `## 分布式锁` 开始。所以按代价从低到高做了三级：

1. `stripToFrontmatter`：剥掉前置寒暄和 ```` ``` ```` 围栏，定位第一行独立的 `---`
2. `salvageFrontmatter`：字段都在只缺分隔符时**把分隔符补上**——只补标点，字段值和正文一个字不动；
   开头不是 `key: value`（比如拒答的一句话）或救出来没正文，一律不碰
3. 还不行才**花一次调用**，把原输出退回去要求「同样内容只改格式重发」

实测格式失败数（每轮 8 页）：**3 → 4 → 0 → 1 → 1**。
中间那次 4 是我把格式要求写得更硬的一轮 —— **n=1，不能说明是提示词写坏了，
只能说明这个指标本身不稳**（跟 opt-22 量到的 judgeSpread 一个道理）。
把失败那一页单独重跑一次，它又完全正确地输出了 frontmatter，
所以这不是某页内容的确定性问题，就是模型输出格式的抖动。

结论：**这条管线的失败率降不到 0，得当成常态处理**。现在的行为是——
失败的那一页在报错里带上模型原话开头（面板上能看出是拒答、截断还是格式跑偏），
**磁盘上该页的旧版本保持不动**，`index.md` 按磁盘实际内容重写。
所以一次部分失败不会丢 wiki，但**失败页可能是上一轮的旧内容**，需要重新生成那一页。

## 知识页（面板）

原来的「资料库」页变成「知识」页，两个页签：

- **wiki 知识**：左目录树（按类型分组 + 计数 + 名称/摘要搜索）+ 右条目
- **原始文档**：原来的资料库整块搬过去，导入/编辑/版本/对比/删除/蒸馏一行逻辑没改

条目页上有的东西：

- 面包屑 `wiki / concept / 分布式锁`
- 条目卡：类型徽章、摘要、**依据块（可点，跳到原文）**、校验结果、别名、**被谁引用**（反向链接）
- 正文按 Markdown 渲染，`[调度服务-sdd#2]` 这种出处标记是可点的
- `[被否决]` / `[历史]` / `[待确认]` 状态标记渲染成带颜色的小标签
- 编辑（改正文和摘要，**保存时重新校验**，不让手改绕过闸门）/ 重新生成 / 删除（只删条目，原文不动）
- 树最下面是 `index` / `AGENTS` / `log` 三个附属文件，点开能看

左侧状态点三色：**绿=正常，黄=依据的原文改过要重建，红=溯源校验没过**。

### 自己写了个 Markdown 渲染器

项目零依赖，装不了 marked，所以手写了约 80 行（`renderMd` / `mdInline`）：
`#` 标题、列表、引用、代码块、行内码、加粗，加上三个我们自己的记号
——`[[条目链接]]`、`[文档#块号]` 出处、`[被否决]` 状态标记。

**全程 `createElement` + `textContent`，一处 `innerHTML` 都没用**：
条目内容来自资料原文 + 模型输出，直接塞 innerHTML 等于给自己开一个 XSS 入口。

## 入口

```bash
npm run kb:wiki                      # 编译全部启用中的资料
npm run kb:wiki -- 调度服务          # 只编译某一篇
npm run kb:wiki -- --model GLM-5.2   # 换模型
```

面板上是「生成 wiki」按钮，接口是 `POST /wiki/build`（`{doc}` 可选）。
另有 `GET /wiki/tree` `GET /wiki/page` `GET /wiki/file` `POST /wiki/save` `POST /wiki/delete`。

事件流里加了 `wiki.built`（哪些条目、几条没过校验、失败清单），所以生成过程和别的内部动作一样可观测。

## 这一版**没有**做的事（按你的决定）

- **`analysis/` 分析页和「把好答案归档回 wiki」**：这是「复利知识」的核心，但依赖 Query 接入，留到之后
- **接入检索**：条目现在还**不参与检索、也不注入**。`catalogForPrompt()` 已经写好（只放通过校验的条目），
  但没有挂到 provider 上——先看生成质量，再决定怎么注入
- **Lint**（跨页矛盾、孤儿页、缺页概念）：下一步
- **entity 页**：靠模型抽实体，质量最不稳，先不生成

## 已知缺口

- **条目还没接入检索**，所以这一步对回答质量的影响是 0。要等步骤 3。
- **生成质量取决于 `AGENTS.md`**，而它现在是我写的初版、没经过多轮迭代。
- **资料库只有 2 篇**，编出来的条目数量少，`concept` 页之间的交叉引用会很稀。
- **一次生成 = 结构 1 次 + 每页 1 次模型调用**（格式跑偏的页面多一次），没有做并发。
- **重建会留孤儿页**：概念页的 slug 由模型决定，这轮叫 `concept/分布式锁`、下轮可能叫
  `concept/redis锁`，旧文件不会自动清理（source 页已经定死，概念页还没）。
  这件事留给步骤 4 的 Lint（「孤儿页」本来就在它的清单里）——
  在那之前不做静默删除，免得连手改过的条目一起删掉。
- **Web 端点仍然没有鉴权 / CSRF 防护**，而这轮新增的 `/wiki/build` 能触发模型调用（花钱）、
  `/wiki/save` 能改知识内容。这仍然是这个项目里最该先补的洞。

面板结构改了（导航项从「资料库」改成「知识」，新增两个页签和 wiki 目录树），
而且 `web.ts` 也改了（新接口），**在跑的 `npm run web` 必须重启**。
