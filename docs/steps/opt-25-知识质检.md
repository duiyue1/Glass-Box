# 优化 25 · 知识质检（综合分 + 五维雷达 + 30 天趋势）

wiki 是 LLM 编译出来的，**质量会随生成轮次抖动**——opt-24 实测：同一份提示词、同一份资料，
几轮之间格式失败数在 0~4 之间跳，有几轮模型压根不写 `summary` / `aliases`。
没有一个能重复计算的分数，「改了 `AGENTS.md` 之后是变好还是变坏」只能靠印象。

## 最重要的一条设计：进趋势线的数字必须是确定性的

五个维度**全部机械计算、不调模型**，所以同一份 wiki 反复跑分数完全一样
（有单测钉住：`同一份 wiki 反复打分结果完全一样`）。趋势线上每一个变化都对应一次真实改动。

这是 opt-22 量到 `judgeSpread = 0.70/2` 之后定下的规矩：会抖的数字画成曲线只会误导人。
所以模型抽检的结果**单独显示，不并入综合分，也不进 `quality.jsonl`**。
你选的是「机械分 + 模型抽检」，我把模型放在了抽检位置而不是打分位置，理由就是上面这条。

## 五个维度

- **溯源可信**（权重 0.3）= 通过溯源校验的条目占比。最重——过不了这关的条目根本不该拿去回答问题。
- **原文覆盖**（0.2）= 被 **concept 条目**引用的原文块占比。
  **只算 concept 页**：source 页天生引用全篇，算进来覆盖率永远接近 100%，这维就废了（有单测钉住）。
- **精炼去重**（0.2）= 不重复的句子占比。这维是**检查「原文块互斥分配」到底有没有生效**——
  deepwiki-open 公开承认的缺陷就是每页独立生成导致跨页重复，重复条目在检索时互相挤占注入预算。
  比对时去掉出处标记和排版记号、只留 ≥14 字的句子（短句在多页里重复是正常的）。
- **时效新鲜**（0.15）= 依据原文没改过的条目占比。复用 opt-24 的 `sourceHash`。
  这是 BookStack / Wiki.js / Outline 都没有的一项——它们不知道一篇文章什么时候不再成立。
- **可检索**（0.15）= 「有摘要」「别名 ≥3」各半分。这两样空着，条目写得再好也召不回来。

综合分 = 五维加权，权重之和为 1（单测钉住，否则不是百分制）。

## 模型抽检

抽 **3 条**（优先 concept 页，按 ref 排序**等距取而不是随机取**——同一份 wiki 抽到同一批，
两次抽检才可比），每条一次调用，让模型按四条判断给 0~2 分：
结论先行 / 出处齐全 / 状态标记有没有漏 / 忠实原文。单条失败只记进 `failed`，不影响机械分。

## 落盘与入口

```
.glassbox/kb/wiki/quality.jsonl    一次一行、只追加（趋势图的数据源）
```

用 jsonl 不用 json 是为了只追加——中断也不会毁掉历史，跟会话日志一个套路。
读的时候坏行直接跳过，一行坏 JSON 不该毁掉整张趋势图。

```bash
npm run kb:audit                            # 只跑机械分，秒级、免费
npm run kb:audit -- --sample 3 --model GLM-5.2   # 加模型抽检
```

- `GET /wiki/audit` 读上次结果 + 30 天趋势（**不调模型、不花钱**）
- `POST /wiki/audit` `{sample:3}` 真跑一次
- 事件流加了 `wiki.audited`（综合分、各维分数与问题数、抽检条数）

## 面板

知识页第三个页签「质检」，空态就是「图标 + 说明 + 开始评估 + 小字」，跑完显示：

- 左：综合分大数字（≥85 绿 / ≥60 黄 / 其余红，跟条目树三色点一个语义）
- 中：**五维雷达**（正五边形网格 + 闭合折线）
- 右：**30 天趋势**折线；只有一次记录时明说「还看不出趋势」
- 下：每维一张卡（分数条 + 口径说明 + 扣分清单，**清单每条可点，直接跳到那个条目**）
- 最下：模型抽检结果，标注「会抖，不进综合分与趋势线」

两张图都是手写 SVG（`createElementNS`）：项目零依赖装不了图表库，而这两张图本来就是
「五个点连成环」和「一条折线」，用不上图表库。

## 验证

- `npm test` **255 全绿**，新增 11 条质检单测：五维口径、权重和为 1、覆盖率只算 concept 页、
  可检索各半分、重复句检测与短句豁免、`sentencesOf` 清洗、stale 由调用方注入、
  **反复打分结果一致**、`pickSample` 确定性且不抽 source 页、抽检解析与单条失败容错、
  历史只追加/排序/超期与坏行跳过。
- `tsc --noEmit --strict` 无错。
- **真实模型实跑**：`npm run kb:audit -- --sample 3 --model GLM-5.2`，18.9s，结果：

  ```
  综合分 90.7 / 100（8 条条目）
    溯源可信  100    8/8 条通过溯源校验
    时效新鲜  100    0 条依据原文已改动
    原文覆盖  81.8   9/11 块被概念条目引用（#0 #1 没有）
    可检索    62.5   3 条缺摘要且别名为 0
    精炼去重  100    0 句出现在多个条目里（共 65 句）
  模型抽检 3 条，均分 2/2
  ```

  两个结论值得单独说：**精炼去重 100 是「互斥分配真的生效了」的独立证据**（65 句零重复）；
  **可检索 62.5 独立复现了 opt-24 末尾人工发现的那 3 条缺摘要/别名**——
  也就是说这把尺子确实量到了真问题，而不是自我确认。
- 连跑两次分数完全一致（90.7 → 90.7，+0），趋势线因此可信。
- 接口用临时端口（`GB_PORT=7799 GB_LLM=fake`）起了一份服务验过 `GET`/`POST`，
  返回 UTF-8 正常，**没有碰你在跑的那个进程**。

## 已知缺口

- **`quality.jsonl` 里只存数字**，不存问题清单。所以「只读上次结果」时雷达画得出来、
  扣分清单画不出来（要重新跑一次才有）。这是刻意的：历史文件不该越滚越大。
- **权重是我拍的**（溯源 0.3 最重、时效 0.15 最轻），没有校准过。
  等步骤 3 把条目接进检索、能用 `eval:kb` 量到「哪一维掉分最伤召回」之后才好定。
- **模型抽检 n=3**，均分是 2/2 这种整数量表，**抖动不比 opt-22 的 judgeSpread 小**。
  它适合当「看看有没有明显问题」的抽查，不适合当验收指标。
- **Web 端点仍然没有鉴权 / CSRF**，这轮又多了一个会花钱的写端点（`POST /wiki/audit`）。
  这仍然是这个项目里最该先补的洞。

面板结构改了（多一个页签 + 一整块质检面板），`web.ts` 也加了接口，
**在跑的 `npm run web` 必须重启**。
