# opt-32 · 上下文预算从"写死 160"改成"窗口的百分之多少"

## 一句话

压缩阈值原来是硬编码的 `160 tok`，现在默认按**模型窗口 × 0.8** 算；顺手修了中文 token 被低估四倍的估算，并给"网关说超窗口了"加了一次压缩重试。

## 为什么

三个毛病，一个比一个隐蔽。

**绝对值没法跟着模型走。** `160` 这个数字对 8k 窗口的模型是"永不压缩"，对 200k 窗口的模型是"每回合都压"。同一份代码换个模型，行为完全不同，而代码里没有任何地方表达"这个模型能装多少"。

**中文被低估四倍。** 旧的估算是 `字符数 ÷ 4`，那是英文的经验值。中文一个字大约就是一个 token，所以一段中文对话显示 160 tok 时，真实用量可能是六百多。绝对值时代这个偏差无所谓（反正数字本身是拍的），但阈值一旦变成"窗口的 80%"，估低就等于**该压的时候不压**，一路涨到网关报错才发现。所以这条是比例阈值的前置依赖，不是可选的顺手优化。

**保留区按条数是个坏尺子。** 原来固定保留最近 2 条。可这两条可能是"好"和"一整个文件的内容"，留下来的量能差上百倍，而模型关心的是 token 不是条数。

## 怎么做

### 窗口是模型的属性

`Llm` 接口加了一个可选的 `contextWindow`（`engine/loop.ts`）。窗口有多大只有模型实现自己知道，引擎不该猜：

- `RealLlm` 从 `GLASSBOX_MODEL_WINDOW` / `MIDSCENE_MODEL_WINDOW` 读，不给就用保守的 `128000`（`llm/realLlm.ts`）
- `FakeLlm` 写死 `200`——`200 × 0.8 = 160`，正好是项目一直用的那个演示阈值。假模型下的行为一个字都没变

后面这条是有意的：真窗口十几万的话，你跑一整天都看不到一次压缩，面板上那格永远空着。演示需要一个小窗口。

### 两种模式

`resolveBudget()`（`app.ts`）：

- **比例模式（默认）**：阈值 = 窗口 × `GB_COMPACT_RATIO`（默认 0.8），保留 = 窗口 × `GB_RETAIN_RATIO`（默认 0.16）
- **绝对值模式**：显式给了 `GB_BUDGET` 就用它，并退回按条数保留最近 2 条

两个默认值抄的是 DeepSeek Harness 的 `dsh-compaction-basic`（`thresholdRatio: 0.8` / `retainRatio: 0.16`）。它还有一条校验值得一起抄：**保留区比例必须小于阈值比例**，否则切点永远算成 0，历史只增不减，一路涨到窗口溢出。这种自相矛盾的配置在启动时就该报错，而不是等运行时表现成"压缩功能好像没生效"。

### 保留区按 token 选

`Session.selectCut()`：从尾巴往前累加 token，够 `retainTokens` 就停。然后**切点往后挪，直到尾巴不是以 `tool` 消息开头**——这条老规矩不能丢，切出一条没有 assistant 配对的 tool 消息，网关直接 400。

这里够用是因为 loop 每次工具调用都成对追加一条 assistant + 一条 tool，不存在一条 assistant 带多个 tool 结果的交错结构。dsh 用的是更通用的做法（按 tool-call / tool-result 计数找平衡切点），我们不需要。

### 溢出兜底

主动阈值可能拦不住（估算偏低、或者系统提示与工具声明本身就很大）。所以加了第二条触发路径，同样是抄 dsh 的 `context-overflow`：

1. `RealLlm` 认出网关错误里的溢出关键词（`context_length_exceeded`、`maximum context length`…），在响应上打一个 `overflow: true`
2. `Loop` 见到它就抛 `ContextOverflowError`——**不能**像别的调用失败那样，把一句"（模型调用失败…）"当成模型的回答写进历史
3. `Session.ask()` 捕获它，压掉一段，原样重试一次。压不动就照实抛出去，不做无意义的第二次尝试

代价说清楚：如果溢出发生在回合中段，重试会把前面那几步工具重跑一遍。只重试一次，比整个回合报废划算。

## 实测

`npm test` 326 条全绿（新增 5 条）。

真实模型（gpt-5.5）四回合实跑，故意把窗口设成 600 好让压缩发生：

```
GLASSBOX_MODEL_WINDOW=600 node src/index.ts "读 package.json 有哪些脚本 ;; 哪个是跑测试的 ;; tsconfig 的 target ;; 总结这三轮"
```

- 面板上的阈值是 `480`（600 × 0.8 算出来的），不再是 160 ✅
- 第三回合末触发压缩：`丢弃 13 条, 618 -> 74 tok` ✅
- 第四回合正常完成，**没有 400**，而且模型只靠摘要就把三件事都说对了 ✅

## 一个实测撞出来的缺口（留给下一步）

第四回合日志里有这么一行：

```
[上下文] 2522/480 tok, 6 条消息
```

历史被压到 74 tok 了，可实际发给模型的是 2522 tok。差额来自**本回合注入的东西**：资料库 693 + 知识目录 228 + 记忆 38，再加系统提示和工具声明。

也就是说：`GB_BUDGET` 管的一直只是"对话历史"这一小块，而窗口要装的是整个请求。真窗口 600 的话，这次请求会真的溢出——阈值改成比例只解决了一半问题。

dsh 的做法是把系统提示、工具 schema、历史一起过秤（`TokenMeter` 量的是 surface 加 requestHeader）。我们现在只秤了历史。这条是 opt-33 的头等事，比"两级压缩"更靠前。
