# opt-28 · 检索改写（Agentic RAG 的最小闭环）

## 这一步做了什么

原来的检索是**一条直线**：构造查询 → BM25 → 阈值筛 → 注入。查不到就是查不到，
模型只能空着手回答（实测过这时它会开始写"常见做法有三种"——nokb 组的 completion token
是 kb 组的 2.3 倍，就是这么烧的）。

外面说的 Agentic RAG 是把直线变成循环：模型自己判断够不够，不够就改写查询再来一轮。
这里做的是**省钱版**，两处不一样：

**一、要不要重试由确定性信号决定，不问模型。**
朴素做法是每回合都让模型自评"这些片段够不够"——那是每回合多一次调用，
在这个项目里绝大多数回合都是白花的。我们只在**一段都没注入**时才启动
（`GB_KB_MIN_TOP1` 可以额外把"命中但分数太低"也算进来，默认关，因为 BM25 绝对分跨库不可比）。
正常回合零额外成本。

**二、模型只负责出检索词，不负责回答。**
它给 2~3 个候选词组，我们逐个去检，然后**机械地**挑最好的（先看注入了几段，再看最高分）。
平手保留原结果——改写要赢得明显才值得换。

一条纪律：**改写完还是空的，就保持不注入。** 不能为了"有东西注入"而硬塞，
评测里 N3 就是被"看起来像答案的片段"带跑的。测试专门钉住了这一条。

新文件 `src/kb/rewrite.ts`（`needsRewrite` / `rewriteQuery` / `normalizeQueries` / `pickBest`），
`kbProvider` 的 `provide` 改成 async（`ContextProvider` 本来就允许返回 Promise，`Loop` 是 `await` 的）。
每次改写都发 `kb.rewritten` 事件：为什么触发、候选是什么、各自命中几段、最后换了哪个。
`GB_KB_REWRITE=0` 关掉。

## 实测：一个确定的收益，一个被推翻的预期

先找一个**真实的零命中问法**（确定性探测，不调模型）：「排班表在哪看？」——
资料里写的是"值班规则/周三值班/交接"，没有"排班表"这个词。

### 确定的：0 段 → 5 段

```
[资料库] 检索改写（零命中）: 排班表在哪看？ → 值班 排班 查看（0→5 段）
[资料库] 注入 5 段(266/800tok)
```

模型的答复也从"不知道"变成了带来源的具体内容，并且如实说了"资料里没有说明排班表在哪看"。

### 被推翻的：以为能省一个来回，实测更慢

我第一次跑完看到 5.6s vs 8.0s，写下了"延迟更低"。多跑两轮就翻了：

```
GB_KB_REWRITE=1 : 11s（0 次工具）, 19s（6 次工具）
GB_KB_REWRITE=0 :  7s（2 次工具）,  7s（2 次工具）
```

**原来的判断是 n=1 的噪声。** 而且更根本的问题在这里——关掉改写的那次，
模型自己调了 `kb_search({"query":"排班表 值班"})`，**自己完成了改写**，拿到了同样的答案。

也就是说：在有原生 tool calling、且模型愿意主动查的前提下，
provider 侧的自动改写**和模型自驱是重叠的**，而且总时长更长。

## 那它什么时候真有价值

把 tool calling 关掉（`GB_TOOLCALL=0`，退回 ACTION 协议）再比一次，差别就出来了：

```
改写开：注入 5 段 → "资料里没有给出排班表的具体查看地址"，然后列出值班规则的原文内容和来源
改写关：注入 0 段 → "排班表看《提效助手内部约定》里的周三值班安排/值班规则部分"
```

**关掉改写那条是编的**——原文从没说排班表在那里，模型是拿知识目录里的一句话摘要
猜了一个位置。这就是"检索不到"的真实代价：它不会说不知道，它会顺着手里那点线索编。

所以这一步的定位很清楚：**它是"模型不会自己再查一次"时的兜底**，不是给会自己查的模型加速。
默认保持开启，理由是兜底的失败模式（编一个位置）比多花一次调用严重；
不想付这个成本就 `GB_KB_REWRITE=0`。

## 为什么没有召回率数字

`eval:kb` 这次量不了：默认预算下 20 条用例的关键词召回已经是 **100%**（天花板），
一条零命中的用例都没有，改写没有触发的机会。紧预算（items=1）下的失败是**预算不足**
导致的，改写不改变预算，救不了。

要想量到，得往评测集里加"问法和资料完全对不上"的用例。那属于改评测集——
自己出题自己考的东西，我不会拿它当收益数字，留给下一步单独做。

## 顺手记下的两件事

- `normalizeQueries` 一开始只清全角标点，结果模型给的「抢锁失败, 重试」和「抢锁失败 重试」
  被当成两个不同候选，白检一次。半角标点也要清。
- `rewriteQuery` 失败（网关 500 / 模型胡说）时返回空数组而**不抛错**：
  改写是锦上添花，它失败不该让整个回合失败——退回"没检索到"的老行为就好。
