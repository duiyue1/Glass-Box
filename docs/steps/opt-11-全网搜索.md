# 优化 11 · 全网搜索（web_search + web_fetch）

## 你选的方案，和它在这台机器上的现实

你选了「爬搜索引擎 HTML，零 key」。开工第一件事是验证这条路通不通：

```
$ curl 'https://html.duckduckgo.com/html/?q=test'
curl: (35) Recv failure: Connection reset by peer

$ curl https://example.com        → 200
$ curl 'https://cn.bing.com/search?q=nodejs'  → 200, 100KB, 含 10 个 <li class="b_algo">
```

**DuckDuckGo 在这台机器的网络里是被重置的**（国内网络的常态），DDG 方案在这儿跑不起来。
所以按你选的思路（爬 HTML、零 key）换了引擎：**默认 Bing（cn.bing.com），DuckDuckGo 作为可选后端保留**，
`GB_SEARCH_PROVIDER=ddg` 切换——在能访问 DDG 的网络里它就能用。

这也是为什么要先 curl 一下再写代码：如果按计划闷头写完 DDG 解析，测试全绿，一上真实网络才发现根本连不上。

## 两个工具，不是一个

- **`web <搜索词>`** → `web_search`：返回 5 条 标题/链接/摘要
- **`fetch <url>`** → `web_fetch`：抓单页正文，HTML → 纯文本

合成一个的话，每次搜索都会顺带抓 5 个页面，token 和时间全浪费。分开后模型可以先看摘要、
再决定读哪一个——实测它就是这么用的：搜 → 看摘要 → fetch 一个。

## 安全：三道闸门

联网是这个 demo 里**风险最高**的能力，因为它同时意味着"数据出去"和"内容进来"。

**第一道：审批分级**
- `web_search` = `confirm`，理由写明"查询词会发送到 bing"
- `web_fetch` = `confirm`；内网地址 → `dangerous`

**第二道：内网/本机地址硬边界**（不经过人类审批）

```ts
const BLOCKED_HOST = [
  /^localhost$/i, /^127\./, /^10\./, /^192\.168\./, /^172\.(1[6-9]|2\d|3[01])\./,
  /^169\.254\./,             // 云元数据 169.254.169.254
  /\.internal$/i, /\.local$/i, /(^|\.)baidu-int\.com$/i,
];
```

和凭证黑名单同一个道理："帮我看下这个内网地址"听起来永远是合理请求。实测：

```
$ GB_APPROVE=all node src/index.ts 'fetch http://169.254.169.254/latest/meta-data/'
[审批] 请求(dangerous): 抓取网页: http://169.254.169.254/latest/meta-data/
[审批] 放行                                    ← 人（或自动策略）点了允许
[联网] ✗ 拒绝访问内网/本机地址: 169.254.169.254   ← 照样不发请求
```

**关键细节：每一跳重定向都要重新检查。** 只查初始 URL 是最常见的漏洞——
`http://evil.com/x` 返回 302 跳到 `169.254.169.254` 就绕过了。所以重定向是手动跟随的
（`redirect: 'manual'`），每跳都过一遍 `urlIssue()`。

**第三道：同一把锁装两层**

`fetchText` 内部会查，`webPlugin.run` 也查一遍。这不是冗余——写测试时我注入了 stub fetcher，
那道锁就随之消失了，测试立刻抓到"被拒绝的地址仍然发出了请求"。
**安全检查必须在调用方，不能只在被调用方。**

另外：`GB_WEB=0` 整体断网；受限子 agent 只给 `web_fetch` 不给 `web_search`——
它只该读父 agent 已经定位到的地址，不该自己发散搜索。

## 成本控制

网页正文最容易吃光上下文预算：

- 下载按字节封顶（`GB_WEB_MAX_KB`，默认 40KB），**流式读取，超限就 cancel**，不把大文件先拉完再截
- 截断必须明说：`（注意：正文超过 40KB，以上为截断内容）`——"截了"和"就这么短"是两件事
- **会话内 URL 缓存**：同一个地址第二次直接命中缓存，省步数、省钱，也少骚扰对方站点

## 又踩了一次"URL 被散文粘住"

这条早就预判到了：URL 比文件路径更容易被污染。第一版只按 URL 合法字符集切，
所以中文说明能切掉，但真实模型给出了这个：

```
fetch https://nodejs.org/api/typescript.htmlNode.js 的 type stripping…
                                        ^^^^^^^ 纯 ASCII，字符集切不掉 → 404
```

补了一条规则：路径以常见网页后缀结尾、后面却紧跟字母时，在后缀处断开。

然后**这条规则自己出了个 bug**：`.html` 被砍成了 `.htm`（正则回溯到了更短的后缀分支），
干净的 URL 全都 404。修法是显式判断——同一位置若能匹配更长的后缀，就跳过短的：

```ts
if (PAGE_EXT.some((e) => e.length > ext.length && lower.startsWith(e, i))) continue;
```

值得记下来的是：**这个 bug 是真实网络跑出来的，不是单测**。第一次单测全绿（70/70），
因为我的测试输入恰好都带尾巴，走的是不回溯的分支。补了一条"干净 .html 不能被砍"的回归断言后才钉死。

再强调一次：这仍然是止血。根治要靠原生 tool calling（参数由 API 保证是 JSON）。

## 验证

单测 11 条（全部注入 stub fetcher，不碰真实网络）：HTML→文本、Bing/DDG 结果解析、
内网地址拦截、被拒地址不发请求、URL 切干净（含 `.htm`/`.html` 回归）、缓存命中、
反爬页识别、`fetchOnly` 拿不到 search、`GB_WEB=0` 完全不注册。总数 59 → 70 全绿。

真实网络：

```
[联网] ✓ search:bing?q=node 22 type stripping 限制 · 368ms · 5 条
[轨迹] 搜索 node 22 type stripping 限制 命中 5

[联网] ✓ https://nodejs.org/api/typescript.html 200 · 35KB · 1462ms
[轨迹] 抓取 https://nodejs.org/api/typescript.html 35KB

[联网] ✗ search:duckduckgo?q=nodejs · 541ms · fetch failed      ← DDG 后端在本机的真实表现
```

真实模型（gpt-5.5）问"Node.js 的 type stripping 有哪些限制，请联网查"：
它先 `web` 搜、再 `fetch` 官方文档页（中间有一次 URL 被粘污导致 404），
然后**换了个关键词重搜**并给出了正确完整的答复。降级路径是通的。

## 第二轮：能搜到，但它只搜不读

上线后第一个真实问题："北京今天天气怎么样"，结果连续 4 次 `web_search`，**一次 fetch 都没有**，
最后回答"没查到，建议你去中国天气网看"。

排查发现三件事叠在一起：

**1）查询词被模型自己的散文污染，把搜索结果带偏了**

```
web_search {"query":"北京 天气 实时 中国天气网 2026年8月15日目前搜索结果仍没有返回可用的…建议你直接查看…"}
→ 第 1 条结果: 北京市_百度百科
```

而干净的查询是好的：

```
$ node src/index.ts 'web 北京天气'
1. 北京天气预报,北京7天天气预报… https://www.weather.com.cn/weather/101010100.shtml   ← 正确
```

所以加了 `cleanQuery()`：只取第一行、遇到句末标点就停、**丢掉超过 20 字的"词"**（关键词不会那么长，
那是解释文字粘上来了）、最多 8 个词。这条比追着标记截断更通用。

**2）页面其实完全能爬——是它没去爬**

我手动验证了目标页面：

```
[联网] ✓ https://www.weather.com.cn/weather/101010100.shtml 200 · 64KB · 404ms
htmlToText 后：15日（今天）雷阵雨 23℃ / 16日（明天）雷阵雨转晴 29℃ / 22℃ …
```

数据就在 HTML 里（字节偏移约 24KB，默认 40KB 上限之内），转文本后清晰可读。
**"爬不到"是假象，真实原因是模型停在搜索阶段不往下走。**

**3）光靠提示词劝不动**

先试了软办法：搜索结果末尾追加"以上只是标题和摘要，要给出具体数值请用 fetch 打开链接"，
提示词里也写了同样的规则。真实模型的反应是——继续换措辞搜第 3、第 4 次。

于是改成硬预算：**每回合最多搜 2 次**（`GB_SEARCH_MAX_PER_TURN`），用完后 `web_search`
直接返回失败并指路：

```ts
return {
  ok: false,
  content: `未执行：本回合搜索次数已用完（上限 ${searchBudget} 次）。` +
           `搜索只能给标题和摘要，现在请用 fetch 打开前面结果里最相关的链接读正文，再据此回答。`,
};
```

配套还有两条：归一化去重（加个标点重搜同一件事挡回去）、**按 `turn.start` 重置**——
预算是"每回合"的，跨回合当然允许重新搜（否则用户下次问同样的事会被永久拒绝，这是我第一版真写出来的 bug）。

效果（同一个问题，同一个模型）：

```
[联网] ✓ search:bing?q=北京 今天 天气 温度 · 399ms · 5 条
[联网] ✓ search:bing?q=北京 天气 实时 · 245ms · 5 条
[轨迹] ✗ 搜索 北京 今天天气 预报 命中 0          ← 预算用完，被挡回去并指路
[联网] ✓ https://www.weather.com.cn/weather/101010100.shtml 200 · 48KB · 238ms
最终回复: 北京今天的天气是**雷阵雨**，当前页面显示**约 22℃**，今天预报**最高 23℃**。
```

和我手动抓到的页面内容一致。

### 这一轮的收获

- **"工具坏了"和"模型不用工具"是两种完全不同的故障**，必须先手动跑一遍工具本身再下结论。
  这次工具从头到尾都是好的。
- **提示词是建议，工具返回值是事实**。想改变模型行为，把约束写进工具的返回值（甚至让它失败）
  比在系统提示里多写一段有效得多——它不能忽略一个 `ok: false`。
- **预算类限制必须绑定作用域**。写成"整个进程只能搜 2 次"就成了新 bug；
  绑到 `turn.start` 上才对。这也说明事件总线的价值：插件想知道"新回合开始了"，订阅一下就行。



## 整体收获

1. **动手前先探一下真实环境**。方案里写着 DuckDuckGo，代码写完才发现网络不通，
   那就是白写——一条 curl 换掉了一整轮返工。
2. **安全检查要放在调用方**。放在底层被调用方看起来更"收口"，但只要有人换掉底层实现，
   锁就没了。测试注入 stub 的那一刻正好暴露了这个。
3. **重定向是 SSRF 的后门**。逐跳复查这件事没有捷径。
4. **止血规则自己也会有 bug**。为了修 A 加的正则引出了 B，而 B 只有真实网络能发现——
   补丁越多，这种二阶故障越多，这本身就是"该换协议"的信号。
5. **截断要说出来**。模型看到 40KB 正文不会知道后面还有，除非你告诉它。
