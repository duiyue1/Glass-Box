## 第 1 批：检索层单独一把尺子（`npm run eval:kb`）

这是本步最有用的产出，而且是被逼出来的。

端到端评测跑一轮 10 分钟、要花模型调用、还带评分噪声。而检索侧的改动
（蒸馏桥、阈值、perDoc、上文补全）只影响一件事：**注入了哪几段**。那就直接量这件事：

> 答案必须出现的关键词，有没有出现在这次注入的正文里？

关键词没被注入，模型再强也只能猜；注入了还答错，那是模型/提示词的问题，不是检索的问题。
两件事分开量，才知道该改哪一边。`src/eval/retrieval.ts` 完全不调模型，秒级、确定性、可以反复跑着调参：

```bash
npm run eval:kb                          # 当前参数
npm run eval:kb -- --digest 0            # 关掉蒸馏桥做对照
npm run eval:kb -- --items 1 --tokens 900   # 收紧预算，让排序质量暴露出来
```

它复刻了 `kbProvider` 的查询构造（含多轮关键词接力），所以量的是线上真实会注入的东西。

## 第 1 批 · a：蒸馏（摘要 + 别名）与「digest 桥」

BM25 只认字面。原文写「抢锁失败」，用户问「获取锁超时」——中文 2-gram 下这两个词
**一个 bigram 都不重合**，检索必然 0 命中。不上向量也能补一半：让模型给每篇资料生成
一句话摘要 + 8~15 个别名（同义说法、口语提问说法），存成一个 `type: 'digest'` 的块。

关键设计：**digest 永远不会被注入**。摘要里没有「30 秒」这种数字，注入它只占预算答不出细节。
它只是桥——命中 digest 说明这篇文档相关，于是给这篇文档的正文块加分，把真正含答案的段落捞出来。
（结构上抄的是 doarchon 的 openkb：`raw/` 存原文，`wiki/concepts` 存编译出的概念页，
检索打在概念页上、答案落在原文里。）

入口都是显式的，因为蒸馏要调模型：`npm run kb:distill`、面板上的「蒸馏」按钮、`POST /kb/distill`。
默认只处理没蒸过的；重新导入会丢掉旧 digest（正文都变了，旧摘要不作数），于是自动进待蒸队列。

真实资料库蒸出来的东西（GLM-5.2）：

```
调度服务 SDD > 摘要与别名
摘要：调度服务设计文档：任务分发、Redis 分布式锁与续租、重试告警、监控口径及锁方案选型。
相关说法：调度服务、任务分发、分布式锁、Redis 锁、抢锁失败、获取锁超时、拿不到锁、
         锁续租、租约过期、续租失败、双持有、强制解锁、一致性哈希、worker 集群、
         重试退避、告警、时钟偏移、NTP 同步、锁泄漏、延迟队列
```

### 实测把第一版实现否掉了

第一版对**所有**命中 digest 的文档加分。检索层评测立刻显示问题：同一篇里每块都加同一个常数，
分数差被压平 → 相对阈值（`minScoreRatio`）拦不住弱命中 → 注入 token 暴涨。
X1 那条从 **123 token 涨到 581**（2 块 → 3 块），而召回一点没变——本来就命中了，不需要救。

改成**只救「字面零命中」的文档**：已经有正文命中的文档不加桥分。
桥只在真正「问法对不上」时才有意义，这不是洁癖，是上面那组数字逼出来的。
改完之后，23 条用例上 `--digest 0.6` 和 `--digest 0` 的注入块数、token 数**完全一致**。

### 诚实的结论：这个桥在当前资料库上量不出收益

关键词召回率：桥开 100%（26/26），桥关 100%（26/26）。收紧到 `--items 1` 也一样。

原因是资料库只有 2 篇 / 11 块，`maxItems=6` 意味着一半以上的块都被注入了，检索几乎不可能漏；
而且我那三条「同义表述」用例其实**并没有真正的字面断裂**（「续期线程」和原文「续租」
仍共享「锁」「多久」等 bigram）。真正零重合的场景只在单测里构造得出来
（`digest 桥：问法和原文一个字都不重合时，靠别名把正文块捞出来`）。

所以现在的状态是：**机制在、成本可控（一次性蒸馏调用 + 索引里多一个块，注入 0 token）、
但收益要等资料库长到几十篇、且评测集里有真正字面断裂的用例才能量出来。**
没有数据支持「蒸馏提升了检索」这个说法，就不写这个说法。

## 第 1 批 · b：停用词把实词切坏了（这个是真 bug）

检索层评测把每条用例真正用的查询串打出来，一眼看到不对：

```
| L2 | 长尾细节 | ... | 跳 率 周指标要求是 ？ |
```

「跳过率」变成了「跳 率」。原因：停用词表里有单字的「过/地/得/着」，而去停用词是正则直接抹，
不认词边界。于是「跳过率」→「跳 率」、「租约过期」→「租约 期」、「地址」→「址」。
中文索引是 2-gram，被抹掉一个字的词**连一个 bigram 都对不上**，等于这个关键词从查询里消失了。

修法：单字停用词只留「的/了」和语气词、代词，把「过/地/得/着」拿掉。

代价与收益都实测了，两边都写清楚：

- 定向证据（`跳过率的周指标要求是多少`）：含 `0.5%` 的段落从**倒数第 1（5/5）升到第 2（2/6）**。
  预算收紧时，这直接决定答案有没有被注入。
- 全集聚合：`items=3` 时修前修后都是 100% 召回；`items=1` 时 81% → 77%（一条用例的差别，
  20 条样本上属于噪声）。**聚合指标上没有看到收益。**

那为什么还要改？因为「把实词切成两半」在任何含这些字的资料库上都会犯，
只是这份 2 篇的资料库刚好靠别的关键词兜住了。改的理由是正确性，不是分数——
分数这边我没测出好处，就不宣称好处。

顺带：「的/了」为什么反而留着不删——实测删掉它们召回更好。2-gram 下连接词会带出
「的重」「了之」这类到处都能对上的 bigram，把 IDF 稀释掉。这类判断以后都跑 `eval:kb` 定，不靠直觉。

## 第 1 批 · c：`kb_search` 支持限定范围

`kb_search` 加了 `doc` / `section` / `topK`。明确限定范围时不再套相对阈值和 perDoc 上限——
调用方已经说清要在哪找了，这时候还卡阈值只会让它什么都拿不到。
查不到时把范围回显出来（`《值班手册》里没有和「年会」相关的内容`），模型才知道该去掉限制重试。

## 端到端评测：两轮之间的抖动比改动本身大

同一套代码、同一个模型（GLM-5.2）、同一批 23 条用例，隔离模式，跑两轮：

- 第一轮（蒸馏前）：命中 96% / 全中 95% / 评分 1.74 / 拒答 67% / 注入 545 tok
- 第二轮（第一版桥，蒸馏后）：命中 73% / 全中 70% / 评分 1.30 / 拒答 67% / 注入 570 tok

差距很大（S2/S3/M2/C1/L2 五条从命中翻成不命中），但**不能归因给蒸馏**：
第一版桥只让 X1/P1/P3/C1/L1 五条的注入内容有变化，而翻掉的五条里只有 C1 重叠。
更可能的解释是 GLM-5.2 本身的采样抖动。

第三轮用最终代码 + `--repeat 2`（每条每组跑 2 次，共 46 次/组）把抖动量出来了：

| 指标 | 有资料库 | 无资料库 |
| --- | --- | --- |
| 关键词命中率 | 90% | 37% |
| 关键词全中率 | 90% | 40% |
| 负例拒答正确率 | 67% | 67% |
| 模型评分均值(0~2) | 1.61 | 0.71 |
| **评分波动(同题 max−min 均值)** | **0.70** | **0.73** |
| 标注来源比例 | 70% | 9% |
| 平均注入 token | 542 | 0 |
| 平均 prompt token | 3657 | 3296 |
| 平均 completion token | 159 | 367 |
| 平均首 token 延迟 ms | 6589 | 13689 |
| 平均回合耗时 ms | 9548 | 22042 |

**0~2 分的量表上，同一条题同一个模型两次之间平均差 0.70 分。**
这就是第二轮「崩掉」的真相：n=1 的端到端结论根本不足以判断一次检索改动是好是坏。
（能站住的仍然是大差异：90% vs 37%、1.61 vs 0.71、无资料库那组 completion token
是 2.3 倍——不知道答案时模型就开始写「常见做法有三种思路……」。）

所以第 1 批的所有判断都改用检索层评测（确定性）做，端到端只用来看有没有整体退化。
X1 那条的注入 token 在最终代码里回到了 123（第一版桥是 581），桥的修复在端到端也对上了账。

## 一个稳定的观察：N3 干扰负例，有资料库反而更容易被骗

N3 问「系统 QPS 上限」，而资料里只有被否决方案（MySQL 行锁）的压测数据「QPS 到 200」。
前两轮**有资料库那组都编了、没资料库那组老实说不知道**；第三轮（46 次采样）两组都是
拒答 1/2——也就是说有资料库时大概一半概率会把被否决方案的数字当成结论。

这不是 bug，是资料库的固有风险：注入的片段看起来像答案，模型就倾向于用它。
第 3 批要做的「注入片段带上下文标签（这是被否决的方案 / 这是历史版本）」就是冲这个来的。
现在先把它当成一条已知的、可复现的失败模式记着。

## 已知缺口

- **资料库太小**（2 篇 / 11 块），检索层评测顶在 100% 召回，量不出排序质量的改进。
  要么导入更多真实资料，要么给评测集配一份专门的、更大的合成资料库。
- **评测集里没有真正字面断裂的用例**，所以蒸馏桥的核心场景在端到端评测里是空白的。
- **端到端评测噪声大于改动效应**：实测评分波动 0.70/2 分，需要 `--repeat 3` 以上才能对小改动下结论，
  成本是时间（23 条 × 2 组 × 2 次 ≈ 21 分钟）。
- **评分器还是同一个模型**（GLM-5.2 既当被测者又当裁判）。
- `POST /kb/distill` 和其它 Web 接口一样**没有任何鉴权 / CSRF 防护**；它还能触发模型调用，
  也就是能被外部请求花钱。目前只监听本机，但这仍然是这个项目里最该先补的洞。

面板上加了「蒸馏」按钮和「已蒸馏」标记，`/kb/list` 多返回了 `digest` 字段——
**在跑的 `npm run web` 需要重启才能看到。**
