# opt-31 · 任务计划（task_plan）

## 这一步做了什么

Loop 原来只有 `maxSteps` 一个刹车，那是**防失控**，不是**防跑偏**。长任务里模型典型的失败
不是死循环，而是干到第 5 步忘了第 2 步答应过的事。Claude Code 的 TodoWrite / Codex 的 plan tool
解决的就是这件事：把意图外化成一份清单，每回合重新看见它。

- `src/plan/plan.ts`：`PlanStore`，一份 `{id, text, status}` 清单 + 机械约束 + 追加日志持久化。
- `src/plan/planProvider.ts`：**有计划就每回合注入**（不是命中才注入——计划的全部作用就是重复看见）。
- `src/plugins/planPlugin.ts`：`task_plan` 工具，三个互斥参数 `steps` / `doing` / `done`。
- `plan.updated` 事件 → 日志、轨迹页、面板都能看到，**包括被机械约束拒掉的那次**。
- `GB_PLAN=0` 关掉（对照组：工具不注册、不注入、系统提示里也不提它）。

## 几个刻意的选择

**不强制。** 短任务建计划是纯浪费，所以没建计划就什么都不注入，零成本。

**约束由代码保证，不靠提示词求模型守规矩。** id 必须存在（报错时列出现有步骤，否则它只能瞎猜）、
同时只能有一个 `doing`、`done` 不能回退、重新规划时**文本相同的步骤保留原状态**
（干完的活不能被重排变回没干）。这些都在 `PlanStore` 里，返回失败原因让模型自己改。

**参数是"多行文本"而不是数组**，因为 `ToolSchema` 只支持 string/number/boolean。
这个限制反过来是好事：它把"一步一行、别写长篇"变成了参数格式本身。上限 12 步 × 80 字。

## 实测：一次否掉、一次撞天花板、一个抓出来的真 bug

工作区是 `/tmp` 下的一次性小项目，模型 gpt-5.5，判据全是机械检查（不用 judge）。

### 第一轮：模型压根不用它

6 项机械可验要求的任务，3 次开 / 3 次关：**质量 6/6 对 6/6**，平手。
但看日志才发现问题所在——**三次开启的跑里，`task_plan` 一次都没被调用过**
（`task_plan` 只出现在"插件加载"那一行）。所以这个平手什么也没证明。

**光有工具不够，模型不知道什么时候该用。** Claude Code 也是在系统提示里明确要求用 TodoWrite 的。
于是加了一条提示（`realLlm.ts` 的 `PLAN_HINT`），并且**只在 `task_plan` 真的注册了时才追加**
（`hasPlanTool(tools)`）——`GB_PLAN=0` 时不注册，也就不该提它。

### 第二轮：会用了，但质量还是天花板，成本是实打实的

换成 8 项要求、跨 4 个文件的任务，3 次开 / 3 次关：

```
质量（机械 8 项）    on 8/8 8/8 8/8   |  off 8/8 8/8 8/8
task_plan 调用       11, 6, 0         |  0, 0, 0
工具步数             44, 40, 28（均 37.3） |  24, 22, 28（均 24.7）
```

- 提示确实起作用：3 次里 **2 次真的用了**，第 3 次仍然没用（不强制的代价）。
- 质量**又撞天花板**：两组都是满分，量不出差异。
- 成本是明确的：**工具步数 1.5 倍**（37.3 vs 24.7），多出来的基本就是 `task_plan` 本身的调用。

一个必须承认的算分错误：我第一版检查器只认 `list({done:true})`，把实现成 `list(true)` 的三次判成失败，
一度得出"plan 组 7.33 分低于对照组 7.67 分"。两种签名都是"按 done 过滤"的合理实现，
改成两种都接受后全是 8/8。**先前那个"plan 让质量变差"的结论是我的检查器造成的，不是实测结果。**

### 结构性发现：单回合任务用不到注入

上面 6 次都是单回合。而计划是在**回合开始时**注入的——模型建计划那一刻，本回合的注入早就发生了。
所以单回合任务里计划只通过工具返回值可见，注入这条路径根本没被走到。
换句话说：**这个功能的价值在多回合，单回合下它是净成本。**

补的两回合实验（第二回合只说"继续按计划做下一步"）验证了注入路径：

```
[上下文] 注入: plan(~27tok)
[计划] 第 2 步 → doing | 1✔ 2▶ 3○ 4○
最终回复: 已完成第 2 步：为 remove(id) 补测试。
```

模型只靠这 27 tok 就知道"下一步"是哪一步。这是这一步唯一算得上收益的证据，而且它是定性的。

### 顺带抓出一个真 bug（已修，和 plan 无关）

第一次跑两回合时，第二回合模型调用直接 400：

```
No tool call found for function call output with call_id fc_XG973kgxu4QpGmv9xQl5nW53
```

根因在 `session.ts` 的上下文压缩：它按**条数**硬切，把带 `tool_calls` 的 assistant 消息切进了
被丢掉的那半，只留下孤立的 `tool` 消息。原生 tool calling 要求这两者必须同时在场，
所以整个下一回合都废掉。这个缺陷早就存在，只有"工具用得多的回合 + 还有下一回合"才会触发，
之前的单回合实验永远碰不到。

修法：切点往后挪，直到尾巴不以 `tool` 消息开头。测试遍历压缩后的历史，
断言每条 `tool` 前面都能找到带 `tool_calls` 的 assistant。

### 又一个：计划日志放错目录，把 Web 服务搞挂了（已修）

用户在面板上验证时，`GET /sessions` 直接把进程打挂：

```
Error: 非法的会话 id: s_20260821_1415_7b0d.plan
    at sessionFile (journal.ts:44) ← listSessions (journal.ts:223)
```

我把计划日志写成了 `.glassbox/sessions/<sessionId>.plan.jsonl`。但**那个目录是会话枚举的命名空间**：
`listSessions` 扫所有 `*.jsonl`、把文件名去掉后缀当会话 id，`xxx.plan` 带点号过不了 `SAFE_ID`
（那条校验本身是对的，它挡的是 `../../etc/passwd`），于是抛错——而它在 HTTP 处理里没人接，整个服务退出。

两处都改了：
- 计划日志搬到 `.glassbox/plans/<sessionId>.jsonl`（新增 `plansDir()`，注释写明为什么不能放 sessions/）。
- `listSessions` 遇到名字不像会话 id 的文件**跳过**而不是抛错。列目录是只读操作，
  目录里混进一个陌生文件不该让服务挂掉。

这是这次开发里第二次犯"没考虑目录已有约定"的错，教训是：往别人的目录里加文件之前，
先看清那个目录的文件名有没有被别的代码解析。

## 面板实测后的四处修补

用户在 Web 面板上按真实用法跑了一轮（规划 → 只做前两件 → 分叉 → "继续做未完成的任务"），
一次就把设计缺陷全暴露了：**12 步用尽，最后两个 `write_file` 被丢掉，活没干完。**
逐条修：

**一、分叉不继承计划（最严重）。** 分叉出来的会话有 22 条历史、却是空计划，
模型只能推倒重建一份文本完全不同的新清单，原来 `1✔ 2✔` 的进度全白干
（"同文本保留状态"那条兜底压根用不上，因为它重写了文本）。
现在 `fork()` 按分叉点时间戳切片取"那一刻"的计划，写进新会话的日志，原会话日志一字节不动。

**二、记账占了干活的工位。** 12 步里 5 步花在 `task_plan` 上。`maxSteps` 的本意是拦
"在真实操作里打转"，不是让记账挤掉写文件。新增 `Tool.free` 标记，free 工具不计入 `maxSteps`，
但单独有个宽松上限（`maxSteps*2`）兜死循环；而且到限时只要这一批调用全是 free 就照常放行——
不然会出现"想标记完成却被拒"的怪事。

**三、参数互斥设计过严。** 模型两次很自然地想合并调用：`steps + doing`（建完计划顺手开工）、
`done + doing`（干完一步接着下一步），都被我拒掉，各白烧一步。
现在只有 `steps + done` 不允许（那种情况序号指改动前还是改动后的计划说不清），
`doing` 可以和任意一个搭配；执行顺序固定为"先建计划/先收尾 → 再开工"，
这样"同时只能一个 doing"不会误伤 `done+doing`。

**四、压缩把"干到哪儿"压没了。** `626→71 tok`，摘要只留用户说过的话，工具干了什么全丢，
下一回合模型重新 glob 满仓库摸索。现在压缩摘要里带一份计划快照（约 30~45 tok）。

### 修完的复跑

同一个两回合任务，真实模型：

```
playground/ → README.md, store.js, store.test.js 三件齐全
npm test 退出码 0
「步数用尽」次数：0        （修之前：2 个 write_file 被丢掉）
计划被拒次数：0            （修之前：done+doing 被拒 1 次）
第二回合注入：plan(~45tok)
两回合末尾各跑了一次自动验证，都通过
```

老实说一句：这次跑里模型只调了一次 `task_plan`（建计划），后面没再标 doing/done。
**它对计划的维护并不稳定**，这是"不强制"的固有代价，前面 3 次里 1 次干脆不用计划也是同一件事。

### 补做的两条（检索去重 + 步数）

**只读检索去重**（新增 `Tool.cacheable`，`glob`/`grep`/`read_file` 标上）：本回合内同名同参
再调一次直接复用上次结果，不重复执行、**不占步数**，并在结果末尾明说"已复用，未重复执行"。
换了写法但结果一模一样时也如实说一句"和早前那次结果完全一样，换写法不会有新信息"。
任何非 cacheable 工具（写文件、跑命令）成功后缓存整体作废——"改完再读一遍确认"仍然真的重新读盘。

**步数**：默认 `maxSteps` 12 → 20；剩 ≤2 步时插一条系统提醒"还有改动没落盘就先写文件，别再检索了"，
只提醒一次。

实测（同一个两回合任务，跑两次）：

```
两次都完成全部四件事，npm test 绿，「步数用尽」0 次
工具步数 46 / 30
缓存复用命中：0 次
"结果雷同"提示：0 次
```

**去重一次都没命中，得说清为什么。** 日志里确实有重复调用（两次跑都读了两遍 `package.json`，
run1 还发了两次 `glob playground/**`），但它们**分散在两个回合里**，而缓存是**每回合**的。
同回合内的重复又常被中间的 `write_file` 清掉了缓存。

所以这一条目前只有单测证明机制正确（复用不执行不占步数、写后作废、雷同提示），
**在真实跑里收益为零**。要让它真正生效得把缓存放到会话级，但那会带来陈旧风险：
用户在面板上手改了文件、或别的进程改了文件，跨回合复用就会喂回过期内容。
`read_file` 可以靠 mtime 兜住，`glob` 没法（新文件不会改老文件的 mtime）。
这个取舍我没擅自做，留着。

能确认的收益来自另一半：**上限 20 之后两次都跑完了**，而 12 的时候同样的任务卡死在
"最后两个 write_file 被丢掉"。代价也直白——步数上限放宽就是用 token 换完成度。

## 测试

`test/plan.test.ts` 13 条：解析（去记号/去重/上限）、空计划被拒、注入内容与 token 量、
"同时只能一个 doing"、"done 不能回退"、未知步骤要列出现有步骤、重复标记 `changed=false`、
`pending` 可直接 `done`、重新规划保留状态且不留两个 doing、持久化（追加+恢复+坏行跳过）、
工具参数互斥、被拒的调用无副作用、`task_plan` 是 safe 工具。
加上压缩配对、压缩带计划快照、`listSessions` 跳过陌生文件、free 工具不占步数、
分叉按时间切片继承计划、`steps+doing` / `done+doing` 合并调用、检索缓存与步数提醒这几条，
全量 `npm test` 321 条通过，`tsc --noEmit` 干净。
