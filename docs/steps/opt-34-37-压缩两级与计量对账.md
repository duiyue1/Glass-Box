# opt-34~37 · 压缩分两级、注入按比例、token 对上账

四件事一起做的，共享同一条实测链，所以写在一篇里。

- **opt-34** 削工具输出（压缩第一级）
- **opt-35** token 估算与网关真实用量对账
- **opt-36** 注入配额从总预算里分
- **opt-37** 摘要交给模型写（结构化八段）——**实测后默认关闭**

## opt-34 · 削工具输出

压缩以前只有一种手段：丢消息。但上下文里最肥的是工具输出（`read_file` 读回来一个源文件动辄一万多字），而它恰恰是**最容易补回来**的——模型要完整内容可以重新调一次工具，而用户说过的话和模型的结论丢了就找不回来。

所以加了第一级：`engine/prune.ts`。超过阈值的 `tool` 消息掐掉中间，留头 + 记号 + 留尾，别的消息一个字不动。

三个设计点都是抄 dsh 的 `compaction-tool-result-pruner`：

**判据用字符数，不用 token。** 这一级不调模型，要的就是确定性和便宜。token 是估的，字符是数的。

**按 Unicode 码点切**（`Array.from(text)`），否则会把 emoji 之类的代理对切成两半，拼回去是乱码。

**幂等**：头尾从「阈值减去记号占位」里分（`头 + 记号 + 尾 <= 阈值` 恒成立），所以削过一次的文本长度已在阈值内，再跑不会二次削减、不会套两层记号。第一版按阈值的固定百分比分头尾，小阈值下 `头 + 记号 + 尾` 会超过阈值，单测直接抓到了不幂等。

默认阈值 2000 字（dsh 是 8192，对这个项目太大——它的工具输出通常几百到两千字）。`GB_PRUNE=0` 关掉当对照组。

## opt-35 · token 对上账

零依赖用不了真分词器，估算准不准过去只能靠猜。但网关的 `usage.prompt` 是免费送上来的真答案——拿它跟自己的估算对一下账，就有了一个机械指标。

`Loop` 每次拿到响应就发一条 `token.estimate` 事件（估算 / 实际 / 偏差率 / 缓存命中），面板和日志都能看到。

这条的价值不只是"诚实"：偏差率不撞天花板、不依赖 judge，可以直接当尺子用。

## opt-36 · 注入配额从预算里分

记忆 40、知识目录 240、资料库 800——这三个数字过去写死，跟窗口毫无关系。窗口 4000 时它们吃掉四分之一预算，窗口 20 万时又只占千分之五。

现在从总预算里分：注入总额 = 预算 × `GB_INJECT_RATIO`（默认 0.25），按「记忆 → 目录 → 资料库」顺序领用，前面省下的归后面。

**关键决定：比例只用来往下收紧，不往上放宽。** 每一路取「按份额分下来的」和「上限」中的小者。那三个默认值是调过的、已知够用的，放大它们没有依据。所以窗口大的时候行为跟以前一字不差，窗口小的时候自动收紧。

领用顺序 = 丢了损失多大 + 能不能靠工具补回来。记忆丢了会重复踩同一个坑；知识目录是指针，模型得先知道有什么才会去查；资料库正文最贵，而且是唯一能被 `kb_search` 主动检索替代的，所以排最后。任务计划不参与分配——它由 plan 自己的条数字数上限兜住，也最不该被挤掉。

顺带修了一处冲突：`FakeLlm` 的窗口原来是 200（为了让 `200 × 0.8 = 160` 正好等于演示阈值），但注入按比例分之后，200 的窗口会把资料库配额压到装不下一块，演示时面板上就看不到注入了。改成 4000，并让**绝对值模式（`GB_BUDGET`）不按比例分注入**——那条路本来就是演示专用，两件事这样互不干扰。想看压缩就 `GB_BUDGET=160`。

## opt-37 · 模型写摘要：做了，但默认关掉

机械摘要只把用户说过的话串起来，工具干了什么全丢。所以按 dsh / Claude Code / Codex 收敛出的那套八段模板（最初的请求 / 关键概念 / 涉及文件 / 出过的错 / 未完成 / 正在做 / 下一步 / 必须遵守的约束）让模型自己写，硬性要求每段都留、空的写"（无）"。

抄了一个不显然的省钱技巧：**不给摘要器另起系统提示**，而是把待压缩消息原样回放、把压缩指令作为最后一条 user 消息追加，工具声明也照原样传。这样这次辅助调用是上一次请求的真前缀，provider 的前缀缓存能命中——实测日志里确实报了 `缓存命中 4096`。

**但实测账不划算，所以默认不开**（`GB_SUMMARY=1` 打开）：

- **慢 5 倍**。同样的三回合任务，机械摘要 1 分钟，模型摘要 4 分 46 秒。每次压缩多花 20~50 秒（看时间戳：`09:19:01 → 09:19:36` 是一次压缩）。
- **压缩比反而更差**。机械摘要 `1414 → 636`（-55%），模型摘要 `1598 → 1394`（-13%）、`2891 → 2416`（-16%）。八段结构本身几百 token，把省下的又吃回去了。
- 换来的是"摘要里保留了工具做过什么"，而这个收益**量不出来**——正是当初把它排在最后的原因。

功能留着、开关留着、单测留着（含"生成失败退回机械摘要"那条）。等有了有区分度的尺子再回来判它的价值。

## 实测

`npm test` 351 条全绿。真实模型（gpt-5.5），窗口 8000（预算 6400）：

```
[Glass-Box] 注入配额: 总额 1600（预算的 0.25）→ 记忆 40 / 目录 240 / 资料库 800
   [上下文] 5147/6400 tok, 4 条消息
   [计量] 估 5147 / 实 3972 tok, 偏差 +29.6%
[削减] 1 条工具输出, 省掉 12463 字
   [计量] 估 5900 / 实 4703 tok, 偏差 +25.5%, 缓存命中 3584
[削减] 1 条工具输出, 省掉 4329 字
[压缩] 丢弃 5 条, 1414 -> 636 tok
```

三件事都拿到了证据：削减一次省掉一万两千字；配额按比例算出来并在窗口大时取上限；对账跑通了。

## 三个新发现

**估算系统性高估 16~30%。** 而且偏差随上下文里中英文比例变化：中文多的时候 +29%，代码（英文）多的时候 +16%。所以 `CJK_TOKENS = 1.0` 偏高，可以往 0.75 调；但这是一个跟内容相关的量，单调一个系数只能减小偏差、消不掉它。高估的方向是安全的（宁可早压缩），代价是白白浪费四分之一窗口。

**系统提示 + 工具 schema 大约 3900 tok。** 窗口 4000 时它一家就超过预算，注入收紧也救不了——那句"固定开销已超预算，压对话解决不了"照旧会打印。这不是 bug，是真实约束：十几个工具的 schema 很贵。要治只能减工具或精简 schema。

**前缀缓存命中量可观**：`缓存命中 3584 / 实际 4703`，七成半的输入是白拿的。这印证了"每回合原封不动重发的内容（比如知识目录那 228 tok）应该挪到系统提示里去"这个方向确实有钱可省。
