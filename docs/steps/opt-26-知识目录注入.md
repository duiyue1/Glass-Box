# opt-26 · 知识目录注入（把 wiki 接进回答链路）

## 这一步解决什么

opt-24/25 花了两步把原文编译成 wiki 条目、再给条目做质检。但有一件事一直没做：

**条目从来没被用过。**

`catalogForPrompt()` 这个函数在 `src/kb/wikiStore.ts` 里写好了，全项目**零调用**。
也就是说：生成、校验、质检、面板、趋势图全都有了，而模型在回答问题时看不到任何条目——
这一层对回答质量的影响精确地等于 0。

这一步就是把它接上，顺带补掉两个拦路的缺口。

## 三件事

### 1. 目录注入：给指针，不给内容

新文件 `src/kb/wikiProvider.ts`，一个 `ContextProvider`，每回合注入一份清单：

```
【知识目录】已整理好的条目如下，需要细节时用 kb_read 读条目（page=ref）或读原文：
- concept/分布式锁 — 调度服务用 Redis 租约锁保护任务执行，含租约续租、nonce 校验…
- concept/归档编号 — 说明归档编号的格式及冲突处理规则
…
```

**它和资料库注入的关键区别：不检索。**

`kbProvider` 是"按这轮的提问去搜，命中才注入"；目录不能这么干——
目录是"这个库里有什么"的地图，命中才给就没有意义了：
模型不知道有这一页，就永远不会想起来去问这一页。

这是外面所说的 **progressive disclosure（渐进披露）**：
先给一张地图，正文要不要读、读哪一页，让模型自己决定并自己付 token。
ContextBench 那份测量（1136 个任务 / 66 个仓库）说的现象是模型普遍"检索太多、只用一点"，
目录的作用就是把"要不要付读正文的代价"这个决定交回给它。

成本被两个数字夹住，都能用环境变量调：

- `GB_WIKI_ITEMS`（默认 20）— 最多列几条
- `GB_WIKI_TOKENS`（默认 240）— 目录整体的 token 上限
- `GB_WIKI=0` — 整体关掉

**砍尾顺序是设计过的**：concept 页排在 source 页前面。概念页才是带具体数值约定、
会被追问的那批；source 页是导航。预算不够时先丢导航页。

两道硬门槛（`pickCatalog()`）：

- **没通过溯源校验的不进目录**。它可能带着编造的数字，而目录是给模型看的"可信清单"。
- **没有摘要的不进目录**。只有一个 ref 的行等于让模型猜这页写了什么，是纯噪声。

落选的条目和原因一起发进 `wiki.injected` 事件——「为什么这页没进目录」
和「为什么这段没检索到」是同一类问题，都必须当场看得见（面板 / 轨迹视图 / 日志三处都显示）。

### 2. 得能读得到：`kb_read` 加 `page` 参数

目录给的是 ref，可模型拿到 ref 之后……读不了。`kb_read` 原来只认 `doc`（原文），
不认条目。这不是小疏漏——**注入的目录里写着"用 kb_read 读条目"，而这条路根本不存在**，
不补上就是骗模型去撞墙。

现在 `kb_read({page:'concept/分布式锁'})` 返回条目的摘要、依据块清单和正文，
未通过校验的条目会带一条警告（「正文里的数字不可信」）。
`GB_WIKI=0` 时这个参数明确回一句「没有启用知识目录」，**不静默退化成读原文**——
静默退化会让模型以为条目不存在。

### 3. 缺的摘要要能补：`--summarize`

上一步的实测记录里写着「8 页有 3 页模型没写 summary/aliases」。而这两样恰好是入口：
摘要空着这页进不了目录（见上面的门槛），别名空着换个说法就召不回来。

新文件 `src/kb/wikiSummary.ts`：只补这两个字段，**不重新生成正文**。
重编译更贵，而且可能把已经通过校验的正文换成没通过的——为补一行摘要冒这个风险不值得。

一道机械闸：**摘要里的数字/标识符必须能在依据原文里字面找到**（复用 `verifyBody`）。
但**别名不校验**——别名的全部价值就在于它是原文里没有的说法
（用户问"抢锁失败"，原文写的是"获取锁超时"），拿溯源去卡它等于把这个功能废掉。
这个区分不是可选项：卡错了这一步就白做。

三个入口：`npm run kb:wiki -- --summarize`、面板上的「补摘要与别名」按钮、`POST /wiki/summarize`。

## 实测（真实模型 gpt-5.5）

**确定性数字（质检的机械分，反复跑完全一样）**：

```
补之前：综合 90.7 · 可检索 62.5（3 条缺摘要、别名 0 个）
补之后：综合 96.4 · 可检索 100  （0 条不齐）
```

`npm run kb:wiki -- --summarize` 一次补齐 3 条，各 5 个别名，0 失败。
补出来的摘要例如「说明归档编号的格式及冲突处理规则」——没有数字，符合规则。

**目录真的进了提示词**：

```
[知识目录] 注入 8 条(140/240tok): concept/任务分发 | concept/值班规则 | … | source/调度服务-SDD
[上下文] 注入: memory(~17tok), kb(~123tok), wiki(~140tok)
```

**`page` 路径模型真的会用**（这一轮我提示了"要看你整理好的那条条目"，是引导性提问）：

```
[工具] kb_read({"page":"concept/时钟与租约排查"})
[工具] 结果: 【条目】concept/时钟与租约排查 【摘要】worker 与 Redis 时钟偏移超过 5 秒…
最终回复: 时钟偏移超过 5 秒会导致续租判断失真… 来源：concept/时钟与租约排查
```

`GB_WIKI=0` 那一跑没有任何目录注入，上下文里只剩 `memory + kb`——对照组是干净的。

单测 266 全绿（新增 11 条），`tsc --noEmit` 零报错。

## 要如实说清楚的三件事

**一、这一步没有"回答质量提升"的数字，一个都没有。**
现有两把尺子都量不到它：`eval:kb` 只量 BM25 检索的关键词召回（目录不参与检索），
`npm run eval` 端到端能量，但 opt-22 实测同题同模型两次之间 judgeSpread=0.70，
目录带来的差异（如果有）大概比这个噪声小。
能站住的只有确定性的那两个：可检索维度 62.5 → 100，目录成本 140 tok/回合。

**二、第一轮自然提问里，目录没改变结果。**
问"归档编号冲突了怎么办"时，资料库被动注入已经命中了正确段落，模型直接答对，
没有去读任何条目——目录那 140 tok 是白花的。
这是预期行为（检索够用时就不该多走一步），但也说明目录的收益集中在
"检索给不全 / 需要跨文档概览 / 需要知道有什么"的问题上，不是普涨。

**三、条目仍然不参与 BM25 打分。**
条目的 `aliases` 现在只有一个用处：写在文件里等着。让条目进检索索引
（换个说法也能命中）是下一件事，不是这一步做完的事。

## 顺手记下的两个坑

- `catalogForPrompt` 原来的兜底是 `p.summary || p.title`。看着稳妥，实际是把
  "没摘要"这个缺陷藏起来——目录里出现一行"concept/值班规则 — 值班规则"，
  模型什么也没得到，而质检那边显示"可检索 62.5"却没人知道为什么要管它。
  改成缺摘要就落选并记原因之后，缺陷才和它的后果对上。
- 补摘要写回时用的是"别名给少了就保留原有的"：宁可不动，也不要用更差的一份
  把已有的覆盖掉。模型输出会抖，写回路径要假设它这次比上次差。
