# Step 3 · 分层 TUI + 玻璃盒实时面板

> 前两步的内部动作都打成了一条平铺日志。这一步把它变成**分屏界面**：左边是对话流，右边是「玻璃盒」——实时显示状态机、插件、工具调用、审批队列、事件流。一眼看清 agent 每一刻在干什么。

---

## 1. 一句话理解这一步

我们没有给引擎加任何新能力，只是给它换了个**仪表盘**。
左半屏像微信聊天窗口（你说什么、AI 做什么、工具返回什么），右半屏像飞机驾驶舱（当前状态、装了哪些插件、正在调哪个工具、哪些操作在等审批）。

关键：**这个仪表盘没有碰引擎一行代码**，它只是订阅 Step1 那条 wire 事件流。这正是当初「一切走事件总线」设计的回报。

---

## 2. 画面长什么样

```
 Glass-Box · 对话                    │ 玻璃盒 · 内部状态
 ─────────────────────────────────  │ ─────────────────────────────
 你> write demo.txt :: 你好          │ 状态机
 AI> [调用工具 write_file]           │   [idle] thinking tool_call tool_result done
   ⟵ 已写入 demo.txt（6 字符）       │
 AI> 工具返回了「已写入…」，任务完成 │ 已加载插件
                                     │   fs, search, shell
                                     │
                                     │ 工具调用
                                     │   ✓ write_file{"path":"demo.txt",...}
                                     │       → 已写入 demo.txt（6 字符）
                                     │
                                     │ 审批队列
                                     │   [confirm] 写入文件: demo.txt → 放行
                                     │
                                     │ 事件流（最近）
                                     │   · 回合开始
                                     │   · → 请求模型 (1 条消息)
                                     │   · ← 模型要调用: write_file
                                     │   · 审批请求(confirm)
                                     │   · 审批结果: 放行
                                     │   · 回合结束
```

- **状态机**那一行会把当前状态高亮出来（真实终端里是反色，管道输出里用 `[方括号]` 表示）。
- **工具调用**里 `✓` 成功、`✗` 被拒/失败、`…` 进行中。
- **审批队列**清楚地记着每个有风险的操作，以及最终放行还是拒绝。

---

## 3. 两个零件

### (1) `tui/renderer.ts`——「事件 → 画面」的翻译器

它内部维护一份**视图状态**（当前状态、插件列表、对话、工具、审批、事件流），
每来一个 wire 事件就更新对应的一块（`apply`），然后 `frame()` 把整份状态画成一帧分屏文本。

它**只消费事件、不认识引擎**。这意味着以后引擎加了新事件（比如 Step5 的记忆事件），只要在 renderer 里加一个分支就能显示，引擎照样不用动。

### (2) `tui.ts`——驱动器

它负责组装引擎、跑一个回合、再把事件流「喂」给 renderer：

- **真实终端**：逐个事件动画式刷新（清屏 → 画新帧 → 停一下），你能**肉眼看着 agent 一步步推进**。节奏由 `GB_DELAY` 毫秒控制。
- **非交互（管道 / CI）**：不做动画，只输出**最终定格画面**，这样输出干净、可被脚本校验。

---

## 4. 一个关键设计：为什么用「回放」而不是「实时刷新」

引擎跑得飞快（一个回合几毫秒），如果实时刷新，你只会看到最后一帧，根本看不清中间过程。

所以这里用了个巧思：**先让引擎安安静静跑完**（Wire 会把每个事件都记进 `history`），**然后再把历史事件一帧一帧地回放**出来，每帧之间停 `GB_DELAY` 毫秒。

- 好处：动画节奏可控、且**完全不拖慢引擎**（不在引擎里插 sleep）。
- 代价：审批用的是自动审批者（`AutoApprover`），因为回放发生在回合结束之后，没法在中途真的弹窗问你。**真人交互式审批**（Step2 的 `InteractiveApprover`）属于「边跑边渲染」的模式，等后续做实时输入循环时再接上——它俩共用同一套 approval 事件，接线成本很低。

## 5. 自己跑一下

```bash
# 在真实终端里看动画（推荐）
npm run tui                                  # 默认写文件场景
node src/tui.ts "grep 事件总线"               # 搜索场景
node src/tui.ts "run rm -rf /tmp/x"          # 危险命令被拒场景

# 调节动画速度（毫秒/帧）
GB_DELAY=500 node src/tui.ts "write a.txt :: hi"

# 放行/拒绝策略同 Step2
GB_APPROVE=all  node src/tui.ts "run ls docs"
```

> 提示：`npm run tui` 通过管道看到的是「最终定格画面」；要看动画，直接在终端里运行。

## 6. 顺带解决的一个真实问题：中文对不齐

终端里一个汉字占 **2 格**、一个英文字母占 1 格。如果按「字符个数」补空格，中英混排的两列就会参差不齐。
`renderer.ts` 里因此写了按**显示宽度**计算的 `dispWidth / truncW / padEndW`（CJK、全角、emoji 都按 2 格算），列才对得齐。这类「字符数 ≠ 显示宽度」的坑，做任何终端 UI 都会遇到。

## 7. 这一步新增的文件

```
src/tui/renderer.ts   # 事件流 → 分屏画面（含中文宽度对齐）
src/tui.ts            # 驱动器：跑一个回合，动画回放 / 定格输出
package.json          # 新增脚本 npm run tui
```

引擎（engine/）、插件（plugins/）**一行未改**——仪表盘完全长在事件总线之上。
