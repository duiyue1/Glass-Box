# 优化 21 · 资料库 A/B 评测（第一把标尺）

在这之前，资料库的每个参数（`perDoc=3`、`minScoreRatio=0.3`、`6 条/800 tok`、要不要带上文）
都是我拍出来的，改完只能凭感觉说「好像准了」。这一步的目标不是让资料库变好，
而是**先造一把尺子**——否则后面所有优化都无法判断是进步还是退步。

做法借了 doarchon 那边的一个机制：它用 `knowledge-mode.ts` 靠工具名反推每次 run 属于
`with_knowledge` 还是 `without_knowledge`，从而能拿同一批任务做对比。
Glass-Box 有完整的事件流，这件事更好做。

## 三件东西

### 1. `GB_KB=0` 对照组开关（`src/app.ts`）

关掉之后：`kbProvider` 不进 providers、`kbPlugin` 不注册（`kb_search`/`kb_read`/`kb_answer` 全不存在）、
`kb.loaded` 不发。**同一份代码的两种跑法**，不是两个分支——否则差异说不清是资料库带来的还是别的改动带来的。

顺带加了 `GB_SESSIONS_DIR`：评测会产生几十个会话，不能混进 `.glassbox/sessions/` 把侧边栏刷爆。

### 2. 评测集（`eval/kb-cases.json`）

13 条，7 个维度。两个设计要点：

- **私有约定（P1-P3）**：答案只存在于《提效助手内部约定》里（值班代号「灰隼」、交接 14:40、
  编号 `TX-7031`、冲突加 200）。模型不可能猜到——这几条是最干净的信号。
- **负例（N1/N2）**：资料里没有的东西。正确行为是明说没有，而不是编。

每条有 `expectKeywords`（答对就必然出现的字面串）和 `reference`（只给评分模型看）。

### 3. Runner（`src/eval/run.ts` + `src/eval/core.ts`）

纯计算部分（指标提取、汇总、解析）单独放 `core.ts`，因为 `run.ts` 一加载就会真的去问模型，
而**指标算得对不对必须能单独测**。

```bash
npm run eval -- --isolate      # 主实验
npm run eval                   # 仓库内跑（测的是另一件事，见下）
npm run eval -- --only F1,P1   # 挑几条
npm run eval -- --judge 0      # 不叫模型评分，省一半调用
```

指标：关键词命中率 / 全中率、负例拒答正确率、模型评分（0~2）、是否标来源、
注入 token、真实 prompt/completion token、首 token 延迟、回合耗时、`kb_*` 工具调用次数。

记忆被强制关掉（`GB_MEM_PERSIST=0`）：不然「数据库问题用英文回答」这类历史原子会同时影响两组，
把信号搅浑。

## `--isolate`：第一个被实测推翻的假设

第一次冒烟跑（工作区 = 当前仓库），P1「周三值班代号」**两组都答对了**。
查明细才发现：对照组虽然没有资料库，但用了 3 次 `grep`/`read_file`
在仓库里翻到了 `.glassbox/kb/raw/提效助手内部约定.md`，于是照样答对——**而且来源标错了**
（说出自《示例-调度服务 SDD》，那篇里根本没有「灰隼」）。

所以加了 `--isolate`：把资料库拷进一个临时空工作区当 workspace，仓库源码不可见。
同一条用例立刻变成 kb 2/2 vs nokb 0/2。

两种跑法测的是两件不同的事，**用之前必须想清楚在问什么**：

- `--isolate`：资料库 vs 什么都没有 —— 知识本身的价值
- 仓库内：资料库注入 vs 让 agent 自己 grep —— 效率。P1 那条实测：
  0 步 / 1576 prompt token / 8.6 秒，对比 3 步 / 8840 token / 22 秒

## 评测框架自己的三个 bug（第一轮数据作废）

第一轮跑完，**我的两个度量器都是错的**。这一段留着，因为它比结论本身更有教育意义：

1. **数字关键词子串误命中**。F3 对照组答「没有统一固定值，常见配置是 100、128、160 之类」——
   明确答错，却拿了 2/2：`160` 真出现了，`10` 是从 `100` 里蹭来的。
   改成纯数字按数字边界匹配 `(?<!\d)10(?!\d)`；顺手让带单位的关键词忽略空格（「5 秒」=「5秒」）。
2. **拒答识别漏了「没写」**。N2 有资料库那组答「文档里没写值班同学的手机号」，
   正则只认「没有写」，被记成「编了✗」，负例拒答率被低报成 50%（实际 100%）。
3. **评分器 prompt 有缺陷**。F2 有资料库那组答案完全正确、还多给了原文里真有的
   `skipped` / `LOCK_BUSY`，评分器给 0 分，理由是「补充了参考答案未提及的细节，属于编造」——
   是我把规则写成了「多说细节 = 编造」。改成「参考答案是要点清单不是上限，
   多给正确细节不扣分，只有与参考答案矛盾或凭空发明数值才扣」。

三条都补了单测，坑的来历写在注释里。修完 F2 从 0 分变 2 分、N2 从「编了」变「拒答✓」、
对照组的关键词命中率从虚高的 53% 降到真实的 38%。

## 结果（gpt-5.5，13 条 × 2 组，`--isolate`，你的 `.env` 原样）

| 指标 | 有资料库 | 无资料库 |
| --- | --- | --- |
| 关键词命中率 | 100% | 38% |
| 关键词全中率 | 100% | 36% |
| 负例拒答正确率 | 100% | 100% |
| 模型评分均值(0~2) | 2.00 | 0.69 |
| 标注来源比例 | 92% | 0% |
| 平均注入 token | 420 | 0 |
| 平均 prompt token | 4226 | 2083 |
| 平均 completion token | 173 | 442 |
| 平均首 token 延迟 ms | 8058 | 9539 |
| 平均回合耗时 ms | 10691 | 15716 |

逐条：13 条里有资料库全部满分；无资料库只有 F2/R1/R2/D1/N1/N2 部分沾到。
私有约定三条对照组全错（把归档编号猜成 `2026-001` / `ZL-2026-001`），
这是意料之中但必须有的对照。

一个反直觉的数字：**无资料库那组 completion token 是有资料库的 2.6 倍**（442 vs 173）。
原因看明细就清楚了——不知道答案时模型会写长篇「常见做法有三种思路……建议 50ms~200ms、
可以用指数退避……」。**注入 420 token 的资料，省下 269 token 的胡扯，还快了 5 秒。**

明细（含每条的完整回答与评分理由）在 `eval/runs/2026-08-19T02-36-39.json`；
`2026-08-19T02-26-41.json` 是度量器修好之前那一轮，留着作对照。

## 这把尺子现在还量不了什么

**天花板效应**：有资料库那组 100% 命中、评分 2.00 满分。
这说明评测集能证明「资料库有用」，但**不能用来调参**——已经满分了，改参数只能变差不能变好。
要给 `perDoc` / 阈值 / 预算调参，需要更难的用例：多轮指代、同义表述（「获取锁超时」问「抢锁失败」）、
跨文档冲突、长距离依赖。

**隔离模式下负例失效**：两组都 100% 拒答。因为空工作区里对照组连文件都没有，
自然说不出话。负例真正有区分度的场景是「资料库里有相近但不相关的内容」，得靠干扰项设计。

**评分器是同一个模型**：gpt-5.5 既当被测者又当裁判。分数只适合看趋势和相对差异，
不适合当绝对质量。要更硬的结论得换一个模型当裁判。

**单次采样**：每条只跑一次，没有做多次重跑取方差。差距大的结论（100% vs 38%）不受影响，
但小差异（比如首 token 延迟 8058 vs 9539）不足以下判断。
