# 优化 12 · 资料库（导入 → 分块 → BM25 检索 → 按需注入）

## 这一步解决什么

在这之前，Glass-Box 的"知识"只有两处：`skills/*.md`（靠触发词命中）和记忆里的 L1 原子
（4 条正则抓出来的短句，预算 3 条 / 40 token）。也就是说：**你手上任何一篇外部资料，模型都读不到**。
想让它知道，只能每次把原文粘进对话——粘一次就占满上下文，还不能复用。

这一步加了「资料库」：你在 Web 面板上把资料导进来，程序按 Markdown 结构切块建索引；
之后你提问时，命中的段落自动注入本回合，并在面板上显示注入了哪几段、BM25 得分多少。

参照对象是内部那份《AI-Ku 技术方案文档》的 doc_store：分块策略（§8）、确定性 chunk id、
`active/archived` 软删除，这些都照搬了。它踩过的坑也躲开了——它把
"BM25 稀疏向量是占位实现（简单词频哈希），生产环境不可用"列成自己的 P0，所以这里直接写真 BM25。
没搬的是 Qdrant / Neo4j / embedding：那需要外部服务，会破掉本项目"零依赖、node 直跑"的前提。

## 为什么不按字数硬切

硬切最省事，但检索命中后注入给模型的会是残片：表格切掉一半、代码块少了闭合围栏、
一句话断在中间。所以 `src/kb/chunker.ts` 按 Markdown 的结构切：

1. **按标题（H1–H6）划分**，块不跨标题；每块记住**标题路径**，如
   `AI-Ku 技术方案 > 9. 权限模型`。这个路径不只是给人看的——它也进检索索引，
   所以按章节名、文档名也能命中。
2. **代码块和表格是原子单元**。代码围栏一路吃到闭合为止，里面的 `#` 不当标题、`|` 不当表格。
   单个块自己就超了 `maxTokens` 也不切——宁可留一个大块，也不给模型半截代码。
3. **过短的块（<50 token）并到上一块**，但只并入**同源标题路径**的块
   （相同，或一个是另一个的祖先）。文档原文说"合并到上一块"，无条件合并会把
   两个不相干的章节粘在一起，标题路径就骗人了。
4. **相邻正文块留 30 token 重叠**，防一句话正好断在边界。代码块和表格不加重叠——
   给它们前面粘一段别的文字，只会破坏结构。

块类型标记 `section` / `table` / `code_block`，和文档 §8 一致。

## 检索：真 BM25，不是"数一下有几个词对得上"

记忆的检索是 `terms.filter(t => text.includes(t)).length`——命中几个词算几分。
它有两个毛病：常见词和罕见词同权重；长文本天然容易命中更多词。BM25 就是修这两点的：

```
idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))
score  = Σ idf(t) · tf·(k1+1) / (tf + k1·(1 - b + b·len/avgLen))
```

- `idf`：某个词在越少的块里出现，命中它越值钱（"Qdrant"比"的"值钱）
- `len/avgLen`：长块的分数被压回去，避免"越长越容易赢"
- `k1=1.5, b=0.75`，常规经验值

中文不分词，沿用记忆检索那套 **2-gram**（"权限模型" → 权限/限模/模型）。够用，
代价是索引里的词条多，个人规模无所谓。

**词频不落盘**：`index.json` 只存 `text`，`tf`/`len` 在 `load()` 时现算。
中文 2-gram 的 tf 表比原文还大，存进去会让索引文件膨胀好几倍。

## 落盘结构与版本

```
.glassbox/kb/
├── raw/<docId>.md   导入的原文，原样保存
└── index.json       { docs: [...], chunks: [...] }
```

- `docId` = 标题 slug（清掉一切非字母数字汉字的字符）。中文保留，文件名可读
- chunk id = `md5(docId::index::version)`，确定性生成——照搬文档 §6.2
- **同标题重复导入 = version+1，旧分块整体删除后重建**。不是往上堆，
  所以改过的资料不会和旧版本同时被检索到（测试里专门验了这点：
  导入 v2 之后搜旧内容的关键词返回 0 条）
- **归档是软删除**：`status='archived'` 后不参与检索，原文和分块都留着，可以恢复

`.glassbox` 本来就在 `.gitignore` 里，所以资料库不会被提交——它是你的本地数据。

## 注入：命中才注入，且必须能看见来源

`kbProvider` 是第三个 `ContextProvider`，和 skills、记忆挂在同一个口子上
（`src/app.ts` 的 `providers: [skillProvider, memory.provider(), kbProvider]`）。
注入内容带来源标注：

```
【资料库】以下内容来自用户导入的资料，回答相关问题时优先采用，并在答复中标明来源标题。
--- 来源: AI-Ku 技术方案 > 9. 权限模型 ---
用户所属部门会展开祖先链……
```

预算 `GB_KB_ITEMS`（默认 4 段）+ `GB_KB_TOKENS`（默认 400 token）双封顶，和记忆一个口径。

同时发 `kb.injected` 事件，面板上显示每段的**标题路径 + BM25 得分 + token**。
这一条是必须的：**看不见来源，就分不清模型是查到的还是编的**。
玻璃盒的整个意义就在这儿——不是"它答对了"，而是"我知道它凭什么这么答"。

注入是本回合临时的，不进持久对话历史（`loop.ts` 的 `injected` 与 `convo` 是分开的），
所以不会一路累积占着上下文。

## Web 面板：多了一页

`header` 加了「对话 / 资料库」两个页签，main 里 `#chat` 和 `#kb` 互相 toggle
（grid 布局下 `hidden` 的元素不占格子，右侧玻璃盒面板照旧）。

三个新接口：

- `POST /kb/import` `{text, title?, source?}` → 切块入库，回 `{doc, chunks}`
- `GET /kb/list` → 文档清单 + 篇数/块数
- `POST /kb/archive` `{id, restore?}` → 归档 / 恢复

文件导入走浏览器端 `File.text()` 读成文本再走同一个 JSON 接口——不做 multipart，
零依赖下手写 multipart 解析不值当。目前只吃 `.md` / `.txt`；
PDF / docx 要解析必须引第三方库，留到后面单独定。

**安全**：
- 请求体上限从 1MB 提到 10MB（贴整篇文档 1MB 不够）
- `docId` 由 slug 生成，`.` 和 `/` 全被清掉，再加一层 `path.dirname(resolved) === rawDir` 兜底，
  标题写成 `../../evil` 也只会落在 `raw/` 里（有测试）
- `/kb/*` 和 `/ask` 一样**没有鉴权**，只靠绑定 `127.0.0.1` 兜着。
  这个新接口会往磁盘写文件，风险比只读接口高——token 鉴权还没做，是待办

## 测试

`test/kb.test.ts`，18 个用例，套件总数 75 → 93 全绿：

- 分块：标题路径、代码块不被切断且里面的 `#` 不当标题、表格整块、短块合并、超长拆分带重叠、空文档
- 检索：BM25 命中（稀有词优先）、按标题命中、条数/token 双预算封顶与丢弃计数
- 存储：版本递增且旧块被替换、归档/恢复、磁盘往返、损坏索引不抛错、空内容被拒
- 安全：`../../evil` 标题不会写到 `raw/` 之外

**已知的验证缺口**：`npm run typecheck` 在这个项目里本来就跑不起来
（零依赖，没装 typescript 也没有 `@types/node`）。临时拉 tsc 跑过一遍，
报的全是 `Cannot find name 'process'` 这类缺 `@types/node` 的噪音，全项目每个文件都一样，
新代码里没有真实类型错误。

## 端到端实测

临时工作区起 `web.ts`，导入一篇两节的文档，问"权限模型是怎么过滤的"：

```
kb.imported  chunks:2 version:1
kb.injected  items:[
  {headingPath:"AI-Ku 技术方案 > 9. 权限模型", score:2.41, tokens:16},
  {headingPath:"AI-Ku 技术方案 > 8. 分块策略", score:0.17, tokens:25}]
llm.request  含 "【资料库】以下内容来自用户导入的资料…"
```

对的那一段 2.41，不相关那段 0.17，差了一个数量级——BM25 的 idf 在起作用。
