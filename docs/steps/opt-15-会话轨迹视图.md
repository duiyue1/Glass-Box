# 优化 15 · Web 会话轨迹视图（列表 / 拖到某一步 / 一键分叉）

opt-14 把会话日志落了盘，但只有 CLI 能看。这一步把它搬到面板上，并且补上一个 opt-14 没做的能力：
**在同一个进程里分叉**。

## 面板多了第三个页签

`header` 里现在是「对话 / 资料库 / 会话轨迹」。会话轨迹页分两块：

- **会话列表**：每行显示首个提问、事件数、时间；分叉出来的会话标注 `分叉自 xxx@seq`；
  当前活动会话标一个绿点
- **轨迹详情**：一个滑块横跨整个会话的 `seq`，拖动时下面两栏跟着变
  - 左：**到该步为止的事件**（`#seq` + 渲染文本）
  - 右：**该步的对话状态**（role + 内容，工具调用标出工具名）
  - 一个「从这一步分叉」按钮

拖动滑块是 130ms 防抖后请求一次，不会每像素都打服务器。

## 三个新接口

- `GET /sessions` → 会话列表 + 当前活动会话 id
- `GET /sessions/view?id=X&to=N` → `{ maxSeq, to, turns, atSeq, lines[], messages[] }`
- `POST /sessions/fork` `{ id, seq }` → 新建会话并把当前对话切过去

`lines` 是**服务端渲染好的文字**，直接复用 `logView.formatEvent`。这样一份渲染器同时服务
CLI 日志、`replay`、和面板轨迹——面板上看到的和 `npm run replay` 打出来的是同一句话，
不存在"两套展示对不上"的问题。

`messages` 走 `rebuildHistory(shown)` 但**故意不传 blobs**：状态预览不需要把图片原图发到浏览器，
占位串 `[image image/png ~2048KB blob:…]` 足够看。

## 进程内分叉：这一步真正的新东西

CLI 的分叉是"起一个新进程 + 重建历史"。面板里不能这么做——服务器只有一个 app 实例。
所以 `App` 新增了 `fork()`：

```ts
const fork = (fromSessionId, seq) => {
  const records = readEvents(sdir, fromSessionId, seq);
  const history = rebuildHistory(records, blobs);
  detachJournal();                       // 从旧日志摘下来
  current = new Journal(sdir, newSessionId());
  detachJournal = current.attach(wire);  // 挂到新日志上
  session.restore(history);              // 对话状态回到那一刻
  wire.emit({ type: 'session.started', ..., forkedFrom: { sessionId, seq: info.atSeq } });
};
```

关键是那个 `detachJournal`：`Journal.attach()` 返回取消订阅函数，分叉时先摘再挂，
所以**新事件只写新文件**。`App.journal` 也从固定字段改成 getter，分叉后指向新的那一份。

两个约束：

- **回合进行中拒绝分叉**（`busy` 时返回 409）。跑到一半换历史会把正在进行的对话搅乱
- **会话 id 必须校验**。面板会把用户点选的 id 发回服务端拼成文件路径，
  不挡住 `../../etc/passwd` 就等于开了任意文件读取。`sessionFile()` 里加了
  `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` 校验并抛错，`web.ts` 再挡一层返回 400

## 验证

**单测**：新增会话 id 安全边界用例，套件 122 → 123 全绿。
`../../etc/passwd`、`a/b`、`a.b`、空串、超长、中文全部被拒；`sessionFile` 抛错，
`readEvents` 对非法 id 直接返回空数组（不碰磁盘）。

**真实模型跑完整链路**（gpt-5.5，临时工作区，浏览器端行为用 HTTP 请求等价复现）：

1. 两个回合：先让它记住"第一个暗号是灰隼"，再记住"第二个暗号是青隼" → `maxSeq=35`，4 条消息
2. 拖到第一个 `turn.end`（#20）：`turns=1`、2 条消息、**状态里没有"青隼"** ✓
3. `POST /sessions/fork {seq:20}` → 新会话，`atSeq=20`，恢复 1 个回合 / 2 条消息
4. 在分叉后的会话里问"我刚才让你记住了哪些暗号"→ **只答"灰隼"** ✓
5. 原会话文件 4792 → 4792 字节，**一个字节没变**；新会话单独一个文件
6. `POST /sessions/fork {id:'../../etc/passwd'}` → 400 非法的会话 id ✓

## 过程中发现的一个真实问题（尚未处理）

第一次跑第 4 步时，分叉后的回答**把"青隼"也说了出来**。查了事件流，原因不在分叉：

```
memory.injected [{"kind":"fact","text":"第二个暗号是青隼…","score":3},
                 {"kind":"fact","text":"第一个暗号是灰隼…","score":3}]
```

是**记忆层**干的。用户那句"再记住：第二个暗号是青隼"被 `记住` 这条正则蒸馏成了 fact 原子，
存在同进程的记忆里；分叉只回退了对话历史，记忆没回退，于是又被注入回来。

分叉本身是对的——第 2 步的状态预览确认了 #20 那一刻没有"青隼"。关掉记忆注入
（`GB_MEM_ITEMS=0`）重跑，回答就只有"灰隼"了。

**这是个设计问题，不是 bug**：记忆本来就被设计成跨会话的长期层（更像用户画像），
而分叉的语义是"回到那一刻"。两者冲突时该听谁的，得定：

- A：记忆保持跨会话（现状）。分叉只回退对话，长期记忆照旧生效
- B：记忆原子记下产生它的 seq，分叉时只注入分叉点之前产生的
- C：分叉时给个选项，让用户选带不带记忆

我倾向 B——它让"分叉"这个卖点自洽，代价是 Atom 多存一个字段。但这会改动跨切面的行为，
所以留给下一步决定，没有擅自改。

## 用默认配置实跑时揪出的两个真 bug（已修）

第一次改用「用户 `.env` 原样配置、不加任何 `GB_*` 开关」跑全链路，分叉后的回答直接是
**「（模型返回为空）」**。查下来是两个独立问题：

**1. 流式解析会丢掉没有换行结尾的最后一行**

把那次失败的请求原样重放：非流式返回正常内容，流式也能收到 39 片 delta。
但 `streamChat` 只在缓冲区里按 `\n` 切行，**流结束后剩在缓冲里的最后一行从来没被解析**。
极端情况下整段回复只有一个 `data:` 行且末尾不带换行，就会整段丢光——
于是「流式返回空、非流式正常」。

修法：把行处理抽成 `handleLine`，读完流之后对残留缓冲再调一次。

**2. 流式返回空时没有回退**

原来的回退条件是「流式**失败**且还没吐字」。但这次流式是「成功但什么都没拿到」，
于是直接把空内容当成了模型的回答。改成：只要没内容也没工具调用，且还没往屏幕上吐字，
就改用非流式重来一次（非流式本身带重试）。

这两条都补了单测：「最后一行没有换行结尾时也不能丢内容」、
「流式返回空内容时回退到非流式」（断言 fetch 被调了 2 次）。

**3. 顺手修的一个显示问题**：资料库注入的来源标注会写成
`调度服务 SDD > 调度服务 SDD > 4.3 分布式锁`——`headingPath` 的第一段本来就是文档 H1，
和 `title` 拼在一起就重复了，模型还会照抄进答复。现在会去重。

## 修完之后用默认配置的完整实跑结果

```
1 原生 tool calling: 值班代号是：灰隼
2 资料库检索: 一共等 14 秒才放弃…锁的 TTL 是 137。来源：调度服务 SDD > 4.3 分布式锁
3 三个回合的 turn.end: [39, 79, 92]  maxSeq 94
4 拖到 #79: turns=2 消息=8 含青隼=False
5 分叉: atSeq=39 恢复 1 回合 / 6 消息；原会话 17005 -> 17005 字节
6 路径穿越: 400 非法的会话 id
```

分叉后的回答仍然带出了"青隼"，事件流里能看到来源是 `memory.injected`——
也就是下面那个还没定的设计问题，不是分叉本身的问题。
