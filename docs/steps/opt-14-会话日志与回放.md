# 优化 14 · 会话日志与回放（黑匣子真的落盘了）

## 之前的问题

`wire.ts` 一共 30 行，事件全在一个内存数组里，**没有上限，进程一退全没**。它唯一的用途是
Web UI 新连接时回放一遍。`session.ts` 的上下文压缩是真删：`this.history = [summary, ...tail]`，
被压掉的原始对话再也找不回来。

也就是说，「玻璃盒」是**关掉终端就碎的玻璃盒**。

## 核心思路：存历史，不存状态

`git` 能 checkout 任意 commit，是因为它存不可变的历史而不是当前状态。同一个道理：

> 把「发生过什么」按行追加进一个只读日志，「回放 / 恢复 / 分叉」就是免费得到的。

Glass-Box 的 wire 本来就已经把每个内部动作变成事件了，只差落盘。所以这一步不是加功能，
是把已有的事件流接到磁盘上，然后三个能力自然掉出来。

```
.glassbox/
├── sessions/
│   ├── s_20260818_1117_ef2e.jsonl    每行一个事件，只追加
│   └── s_20260818_1118_ca6f.jsonl    从上面第 29 步分叉出来的
└── blobs/
    └── <sha256>.b64                  图片原图，按内容哈希去重
```

每行 `{"seq":29,"ts":...,"type":"turn.end","messages":[...]}`。**`seq` 是单调递增序号——
回放到某一步、从某一步分叉，靠的都是它。**

## 为什么能从事件重建对话

`turn.end` 事件本来就带着该回合结束时的完整对话（`messages`）。所以：

```ts
// rebuild.ts
for (const r of records) if (r.ev.type === 'turn.end') last = r.ev.messages;
```

取「目标 seq 之前最后一个 `turn.end`」，就是那一刻的 `Session.history`。不需要重放工具、
不需要重新问模型——恢复是纯读盘操作。

**回合跑到一半被 kill 时，恢复到上一个完整回合**。这是对的：半个回合（有 assistant 的
tool_calls、没有对应的 tool 结果）喂回模型只会让它困惑，原生 tool calling 下网关还会直接报错。

## 图片：这一步最容易做错的地方

`redact.ts` 原来把图片换成 `[image image/png ~2048KB]` 这样的占位描述，理由写在注释里：
一张 3MB 的图会在 `llm.request` / `tool.result` / `turn.end` 里各存一份，还会发给每个新连接的浏览器。

**但这意味着直接从事件重建对话会丢图。** 所以改成外置：

```
[image image/png ~2048KB blob:0d1a…（64 位 sha256）]
```

原图按内容哈希写进 `blobs/<sha256>.b64`。三个好处一起拿：

- 事件流依然很小（引用就是一行文本）
- 回放能把图**无损**还原（`restoreImages` 按 sha 取回）
- 同一张图反复出现只占一份磁盘（哈希天然去重）

没配 `BlobStore` 时占位串格式和原来完全一样，所以旧测试一行没改。

## 三个新能力

**回放** —— 和实时日志共用同一个渲染器：

```bash
node src/replay.ts                      # 列出所有会话
node src/replay.ts <sessionId>          # 重播
node src/replay.ts <sessionId> --to 42  # 只放到第 42 步
node src/replay.ts <sessionId> --json   # 原始事件
```

这里做了一次真实的去重：把 `index.ts` 里那一大段事件渲染 switch 抽成 `src/logView.ts`，
实时日志和回放都用它。**回放不是"另做一套展示"，而是把同样的事件再喂一遍同一个渲染器**，
所以回放出来的和当时看到的一模一样。

**恢复** —— 追加到同一个文件，`seq` 接着往下编号：

```bash
node src/chat.ts --resume s_20260818_1117_ef2e
```

**分叉** —— 新建一个会话文件，头一条 `session.started` 记 `forkedFrom`，
**原会话一个字节都不动**（append-only 的意义）：

```bash
node src/chat.ts --resume s_20260818_1117_ef2e --at 29
```

## 顺手修掉的两个缺陷

- **内存日志加了环形上限**（`GB_WIRE_KEEP`，默认 2000）。完整历史在磁盘上，内存只需够 Web UI
  回放最近进度。之前长会话 + 读图会让它一直涨。
- **上下文压缩从「丢弃」变成「折叠」**：上下文里不带了，但日志里还在，`replay` 随时能翻回去。

## 验证

**单测**：新增 `test/journal.test.ts` 15 个用例，套件 107 → 122 全绿。

- blob：外置后能无损还原、同图只落一份、无 store 时占位串向后兼容、取不到的引用不炸
- 日志：seq 连续、`--to` 截断、续跑接着编号、**半行损坏（进程被 kill）跳过坏行不影响其余**、
  `listSessions` 带首个提问与分叉来源
- 环形缓冲到上限后丢最老的
- **重建无损性（核心断言）**：跑一个带图片的真实回合，
  `assert.deepEqual(rebuildHistory(events, blobs), convo)` —— 重建结果必须和原始 history 完全一致；
  同时断言事件流里不出现 base64 原文
- 重建：半个回合时退回上一个完整回合；没有完整回合时返回空
- 分叉：读到指定 seq 重建，且原文件字节数不变

**真实模型实跑**（gpt-5.5，临时工作区，`GB_MEM_PERSIST=0` 关掉记忆，
确保跨进程唯一的信息来源就是重建出来的历史）：

1. 第一个进程：读 `note.txt`（内容是"值班代号：灰隼"）→ 答出"灰隼"，落盘 4693 字节

2. **换一个新进程** `--resume`：问"我刚才让你读的是哪个文件？里面的值班代号是什么？"

```
AI> 你刚才让我读的是 `note.txt`。里面的值班代号是：灰隼。
```

记忆是关掉的，所以这个答案只可能来自从磁盘重建的对话历史。文件从 4693 追加到 9346 字节，
`seq` 从 31 接着编到 62。

3. `--at 29` 分叉（第 29 步是第一个回合结束）：

```
[会话] 分叉自 s_20260818_1117_ef2e@29：恢复了 1 个回合、4 条消息
AI> 那个代号是：灰隼。你一共问过我 2 次问题。
```

新会话写自己的文件；**原会话 9346 → 9346 字节，一个字节没变**。它答"2 次"也对：
分叉点只有 1 个回合，加上当前这次正好 2 次。

4. `replay` 两条线都能重播，`#seq` 对得上，末尾提示怎么继续/分叉：

```
#   1 [03:18:49.848] [会话] 新建 s_20260818_1118_ca6f（分叉自 s_20260818_1117_ef2e @29）
#  10 [03:18:49.851] >> 回合开始: "那个代号是什么？…"
回放结束：39 个事件，1 个完整回合，最后一个回合结束于 #37
```

**验证缺口（说清楚）**：图片外置的完整链路（Loop → blob 落盘 → 重建还原）是用单测里的
假模型 + 真 FileBlobStore 跑通的，**没有用真实多模态请求走一遍**。原因是要真实模型主动
`read_file` 一张图才能触发，成本高于收益；代码路径和单测走的是同一条。

`npm run typecheck` 仍跑不起来（零依赖，没装 typescript/@types/node）。临时拉 tsc 跑过，
只剩 `src/web.ts:11` 的 `import.meta.dirname` 这个既有噪音。
