# opt-33 · 预算过秤整个请求，压缩挪到发请求之前

## 一句话

预算原来只秤"对话历史"，现在把**系统提示 + 工具声明 + 本回合注入**一起过秤；压缩也从"回合之间压一次"改成"每次发请求之前都压一次"。

## 为什么

opt-32 实测留下的那行日志：

```
[上下文] 2522/480 tok, 6 条消息
```

历史已经压到 74 tok 了，可实际发出去的是 2522 tok。差额全在**压不掉的那部分**——资料库注入 693、知识目录 228、记忆 38，再加系统提示和工具 schema。

也就是说 `GB_BUDGET` 一直在管一个不重要的量。真窗口稍小一点，这个请求就会溢出，而面板上显示"预算充裕"。

第二个毛病：压缩只发生在 `Session.ask()` 开头，也就是回合之间。但撑爆上下文的东西恰恰是**回合内长出来的**——一次 `read_file` 读回五百 token，连读三个文件就顶到窗口。回合开始时压一次根本管不到它。

## 怎么做

### 抽出 Compactor

压缩规则原来长在 `Session` 里。现在抽成 `engine/compact.ts` 的 `Compactor`，因为有两处要用同一套规则：

- `Session` 在回合之间压跨回合历史，上限就是总预算
- `Loop` 在**每次发请求之前**压本回合对话，上限是总预算减掉固定开销

`app.ts` 建一份实例，两边共用，保证保留规则一致。

### 固定开销由模型自己算

`Llm` 加了可选的 `overhead(tools)`：只有模型实现知道自己会往请求里拼什么。

`RealLlm` 算的是系统提示（`NATIVE_GUIDE` 或 `PROTOCOL`，加上 `PLAN_HINT`）加上原生模式下序列化出来的工具 schema——工具一多，schema 比系统提示还贵。`FakeLlm` 不实现，当 0，因为它不发系统提示。

`Loop.runTurn` 里：

```ts
const fixedTokens = estimateTokens(injected) + (this.llm.overhead?.(specs) ?? 0);
// 循环里每次发请求前：
this.compactor?.compact(convo, this.budget - fixedTokens);
```

固定开销在一个回合里不变，所以只算一次。

### 保留区改成"占可用空间的比例"

原来 `retainTokens` 是按窗口算的绝对值（窗口 7500 → 1200）。实测直接翻车：

```
[压缩] 丢弃 1 条, 1405 -> 1414 tok
```

固定开销吃掉 4600，留给对话只有 1400，而保留区要 1200——一次只够丢一条消息，而摘要前缀加计划快照比那一条还贵，**"压缩"把上下文顶大了**。

改成比例：`retainRatio = GB_RETAIN_RATIO / GB_COMPACT_RATIO`（0.16 / 0.8 = 0.2），保留区始终是"这次允许占多少"的两成。好处是没有固定开销时，`budget × 0.2` 正好等于 `窗口 × 0.16`，跟 dsh 的口径一致；有固定开销时它自己会缩。

### 两条从 dsh 抄来的硬校验

**摘要必须比它替换掉的内容小**，否则不换（`region.ts` 里 dsh 是直接抛错）。这条就是上面 `1405 -> 1414` 的解药。

**切点落在 tool 消息上时必须往前挪，不能往后挪。** opt-33 写出来才发现 opt-32 那版的挪法是错的：往后挪等于缩小保留区，而保留区只剩一条大工具结果时会直接挪出界，`selectCut` 返回 0，压缩**静默失效**。opt-32 的实测没暴露它，因为那次保留区覆盖了好几条消息；加上回合内压缩之后（工具结果直接落在保留区里）它立刻显形。往前挪是把那条 tool 的 assistant 一起留下，配对同样完整，而且永远不会挪出界。

## 实测

`npm test` 328 条全绿（新增 2 条）。

真实模型（gpt-5.5）五回合，窗口设 7500（预算 6000）：

```
[上下文] 5107/6000 tok, 4 条消息      ← 第一回合就有 5107，固定开销进账了
[压缩] 丢弃 17 条, 1165 -> 580 tok    ← 回合内压缩，减半
[上下文] 5588/6000 tok, 6 条消息      ← 压完回到预算以内
```

对比 opt-32 同样的跑法是 `2522/480`（超 5 倍且不压）。压缩发生在第四回合**内部**（读完文件之后），不是回合之间——正是这一步要的效果。全程没有 400，模型最后正常总结了四轮做的事。

## 又一个显性化出来的问题（下一步）

窗口设 4000 时会看到这句新加的提示：

```
[Glass-Box] 系统提示+工具声明+注入已占 4900 tok，超过预算 3200；
压缩对话解决不了，请调大窗口或收紧注入预算
```

这不是 bug，是过秤把真相摊开了：**注入预算是写死的绝对值**——`GB_KB_TOKENS=800`、`GB_WIKI_TOKENS=240`、`GB_MEM_TOKENS=40`，跟窗口毫无关系。窗口 4000 时它们占 27%，窗口 200000 时占 0.5%。

这跟 opt-32 修的是同一类病（绝对值 vs 比例），只是换了个地方。下一步应该让注入预算也从总预算里分配。
