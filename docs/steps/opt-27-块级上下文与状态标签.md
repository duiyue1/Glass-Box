# opt-27 · 块级上下文与状态标签（Contextual Retrieval）

## 先说一个纠正

我原本给的方案是「把『这块出自哪篇哪章』拼进 BM25 语料」。**那件事项目早就做了**——
`src/kb/store.ts` 建索引时用的语料一直是 `title + headingPath + text`。实测证据（不调模型）：

```
例外情况       => 提效助手内部约定 > 例外情况#2 (8.58)
概述           => 调度服务 SDD > 1. 概述#1 (2.49)
时钟与租约排查 => 调度服务 SDD > 5. 时钟与租约排查#6 (15.54)
```

这三个词在对应块的**正文里一个字都没有**，只出现在章节标题里，照样命中。
照原话去做就是第二个 digest 桥——空转。

所以这一步做的是它真正缺的那一半：**块级、LLM 写的上下文 + 状态标签**。

## 这一步做了什么

`src/kb/context.ts`：离线给每一块补两样东西。

- **一句话上下文**：「这段在讲什么」。块被切开之后开头常常是上一节的尾巴
  （实测：`#6` 挂在「5. 时钟与租约排查」标题下，正文却从重试退避开始），
  这一行是判断「这段到底讲什么」的唯一线索。
- **状态**：`current / rejected / historical / mixed / unknown` 五档枚举。
  用枚举不用自由文本，是为了能机械校验——模型写歪了直接判非法。

两个刻意的设计：

**一次调用处理整篇，不是每块一次。** 省钱是次要的。主要原因是
「这段属于被否决的方案」这个信息**只存在于全文里**，单看一块判断不出来。

**`mixed` 这一档是真实语料逼出来的。** 原本只想给四档，结果发现 `#3` 这一块里
既有现行的抢锁重试约定，又有整段「我们明确否决过的三个方案」——长块 + 重叠切分下
这是常态。硬塞进"现行/已否决"二选一只会得到一个错标签。

**机械闸**：那句话里的数字/标识符必须能在**它自己那块**里字面找到（复用 wiki 的 `verifyBody`）。
提示词已经写了"不要写数字"，这道闸是兜底：它要进提示词，自己编个数出来等于在源头造幻觉。

注入长这样（`current` 不标状态，省 token）：

```
--- 来源: 调度服务 SDD > 3. 分布式锁 ｜ 状态: 含已否决/历史内容（注意区分） ---
（这段：分布式锁实现与方案取舍）
正文…
```

入口：`npm run kb:ctx`、面板「补块上下文」按钮、`POST /kb/context`。
重新导入 / reindex 会重建分块，`context` 字段随之消失——内容变了旧描述就不该算数
（和 digest 失效同一个套路），`needsContext()` 会把这些文档重新列出来。

## 实测（真实模型 gpt-5.5）：一个赢的，一个没赢的

11 块一次跑完（2 篇资料 = 2 次调用），0 块被机械闸拦下，0 块模型漏给。
状态分布：10 块 `current`，1 块 `mixed`——就是那块装着「压测时 QPS 到 200」的。

### 没赢的：进 BM25 语料，召回零收益

我原本以为"模型用自己的话写的一句，词面比原文宽，同义问法能靠它对上"。
实测把这个假设否掉了：

```
默认预算（6 条/800 tok）： 关键词召回 100% → 100%   全召回用例 20/20 → 20/20
紧预算（1 条/200 tok）：   关键词召回  58% →  58%   没召回的用例是同一批 10 条
```

紧预算那一栏尤其说明问题——**连失败的用例都是同一批**，一条都没救回来。
而且它还有害：那 10 来个字进了词表，`len` 归一化跟着变，边界命中会翻个儿。
实测到两处：N3 那条查询关着的时候第三块是「值班与联系人」，开了变成「分布式锁」；
C1 的注入从 219 tok 掉到 123 tok（检索集合变了，不是省了 token）。

**零收益 + 扰动排序 = 默认关掉**。`GB_KB_CTX_INDEX=1` 保留这条路，
等 KB 长到几十篇、评测集里有真正字面断裂的用例再测。
默认关掉之后每条用例的注入块数和 `--ctx 0` 完全一致——排序回到了原样。

（为什么会零收益，事后看是清楚的：语料里本来就有标题和章节路径，
这一句 14 个字的话在 2-gram 词面上和它们高度重合，能新增的词很少。
digest 桥那次踩的是同一类坑——**以为会赢，实测没赢**。）

### 赢的：状态标签在注入文本里确实出现

```
Q: QPS 到 200 是什么意思
   --- 来源: 调度服务 SDD > 3. 分布式锁 ｜ 状态: 含已否决/历史内容（注意区分） ---
Q: MySQL 行锁方案为什么不用
   --- 来源: 调度服务 SDD > 3. 分布式锁 ｜ 状态: 含已否决/历史内容（注意区分） ---
```

以前这两次注入给出的正文和现行约定长得一模一样，模型没有任何线索。

**但不能说「治好了 N3」**：N3 的原题「调度服务的 QPS 上限是多少？」在当前检索参数下
**根本没检索到那块**（注入的是概述和值班两块）。也就是说标签在这条用例上没机会起作用。
它真正生效的场景是"被否决内容确实被检索到了"——上面那两个问法是证据，N3 原题不是。

### 成本：比我估的低

我说过每块 +20~30 tok，**实测是 +7 左右**（模型写的一句话只有 10~14 字，
状态标签只在非现行块出现）。每条用例的注入总量涨 7~38 tok：

```
F1 712 → 750    P2 45 → 61     C1 219 → 254    L1 458 → 470
```

顺手修了一处口径 bug：预算原来只按正文 token 算，注入时又多塞一行，
报出来的 `usedTokens` 就是假的。现在 `costOf()` 把那一行算进去了——
玻璃盒里报的数字必须是真花掉的数字。

## 结论（可以直接引用的部分）

- 状态标签有用，保留并默认开启（`GB_KB_CTX=0` 关）。
- 一句话进 BM25 语料在当前规模下没有收益，默认关闭（`GB_KB_CTX_INDEX=1` 开）。
- 成本 +7 tok/块，`usedTokens` 现在是真实值。
- **没有拿到的**：这一步不能宣称提升了回答正确率。召回是 100% 天花板（量不出），
  N3 原题没检索到那块（标签没机会起作用），端到端有 judgeSpread=0.70 的噪声盖着。
