# 网关服务 SDD

示例文档，用来测试资料库在多篇长文档下的检索表现。测完可以在资料库页归档或删掉。

## 1. 概述

网关服务是所有外部流量进入内部服务的唯一入口，承担四件事：鉴权、限流、熔断、灰度路由。服务本身无状态，实例之间不共享内存状态，所有需要共享的计数都放在 Redis 里，但**限流的主路径不依赖 Redis**（原因见第 3 节的方案取舍）。网关部署在两个机房，每个机房 12 个实例，实例之间通过注册中心互相发现，用于全局限流的窗口聚合。

网关只做协议转换和流量治理，不做业务逻辑。任何需要读写业务表的需求都不能放在网关，这条是硬约定：网关一旦挂掉全站不可用，它的代码复杂度必须控制住。历史上有两次把业务判断塞进网关的尝试，都在评审阶段被拒绝，理由记在第 6 节。

## 2. 鉴权

外部调用一律走签名鉴权，不接受明文 token。签名算法是 HMAC-SHA256，参与签名的字段有五个：调用方服务名 `caller`、请求路径、请求体的 SHA256、时间戳 `ts`、随机串 `nonce`。签名结果放在 `X-Signature` 头里，密钥由密钥管理服务下发，每 90 天轮换一次，轮换期间新旧两把密钥同时有效，重叠窗口是 24 小时。

签名有效期是 300 秒。超过 300 秒的请求直接拒绝，返回 `AUTH_EXPIRED`。这个值不是随便定的：我们统计过调用方到网关的 P99 网络延迟是 1.2 秒，300 秒给了 250 倍的余量，足够覆盖调用方机器时钟不准的情况，同时又短到让重放攻击的窗口没有实际意义。

时钟偏移的容忍范围是 ±60 秒，也就是说请求里的 `ts` 可以比网关的当前时间早 300 秒、晚 60 秒。允许"晚"是因为调用方的时钟有可能走快，实测线上有少量机器快 20 到 40 秒。注意这个 60 秒和调度服务里那个 5 秒完全是两件事：调度服务卡的是 worker 与 Redis 之间的时钟偏移，影响的是租约续期判断；网关卡的是调用方与网关之间的偏移，影响的是签名有效性。两个数字不要互相套用，这在一次事故复盘里被搞混过。

`nonce` 存在 Redis 里做去重，key 的 TTL 就是 300 秒，和签名有效期对齐。这里有个容量约定：单个调用方每秒最多 2000 个不同的 nonce，超过之后 Redis 写入会被降级为"不去重"，只记一条告警。我们接受这个降级，因为签名本身仍然有效，去重只是防重放的第二道锁。

## 3. 限流

限流分两层，单实例本地限流 + 全局限流，两层都用令牌桶。

单实例的 QPS 上限是 800。这个数字来自压测：单实例在 800 QPS 时 CPU 使用率约 65%，P99 延迟 18 毫秒；到 1200 QPS 时 P99 涨到 90 毫秒并开始出现 GC 停顿，所以取 800 作为工作点，留出应对突发的余量。桶容量设成 1600，也就是允许两秒的突发，超出直接返回 `RATE_LIMITED`，不排队。

全局限流的上限是 5000 QPS，按调用方维度聚合。每个实例每 200 毫秒把自己的计数上报一次到 Redis，然后读回全局窗口的总量，用总量除以实例数得到自己这一档应该放多少。这个做法有 200 毫秒的滞后，也就是说极端情况下全局实际放行量可能短暂超过 5000，实测超出幅度在 8% 以内，业务方接受这个误差。

关于限流有三个我们明确否决过的方案，记在这里避免以后重复讨论。第一个是在 Nginx 层用 `limit_req` 做限流：好处是不占业务进程资源，坏处是 Nginx 的限流粒度只能按 IP 或 server 维度，拿不到调用方服务名，而我们的配额是按服务名分配的，因此放弃。第二个是所有限流都走 Redis 计数器：语义最准确，但每个请求都要一次 Redis 往返，压测时单实例 QPS 到 300 就被 Redis 的 RTT 拖住了，而且限流 key 是天然热点，Redis 单分片扛不住全站流量，因此放弃。第三个是用 Sentinel 这类现成的限流组件：功能足够，但它的规则推送依赖自己的控制台，和我们现有的配置中心是两套东西，运维上要多维护一个系统，评估之后认为收益不值当。综合下来，本地令牌桶 + Redis 异步聚合是当前的选择，代价是全局精度有 8% 左右的误差，这一点在接入文档里对业务方明确写清了。

限流的历史版本值得记一下：v1 时期我们按客户端 IP 限流，上限是每 IP 每秒 50 个请求。这套在 2025 年 11 月就废弃了，原因是大量调用方走的是同一批出口 NAT 地址，按 IP 限流会让老实的调用方被别人的流量连带打死。**现在的实现里已经没有任何按 IP 限流的逻辑**，如果在配置里看到 `ip_qps` 这类残留字段，那是没清理干净的死配置，可以忽略。

## 4. 熔断

熔断器按"调用方 + 下游服务"这个二元组维度独立统计，不是全局一个熔断器。判定条件是滑动窗口内错误率超过 50% 且持续 10 秒，窗口长度 10 秒、分 10 个桶。触发之后熔断器打开 30 秒，这 30 秒内的请求直接返回 `CIRCUIT_OPEN`，不再打到下游。

30 秒之后进入半开状态，放行 3 个探测请求。三个全部成功才关闭熔断器，任意一个失败就重新打开并把等待时间翻倍，最长翻到 240 秒为止。这里刻意用"3 个全成功"而不是"成功率过半"，因为半开阶段样本太少，过半的判据在 3 个样本上等价于 2 个，抖动一次就误判为恢复。

错误率的分母只算"真正打到下游的请求"，被限流拒掉的不算。这个口径很重要：如果把限流拒绝也算成错误，那么一次流量高峰会同时触发限流和熔断，熔断打开后下游反而空闲，形成误判连锁。这个坑我们踩过一次，见事故复盘里的 INC-2077。

熔断相关的指标有三个：熔断打开次数（按二元组统计）、半开探测失败次数、熔断期间被拒绝的请求数。第三个指标是业务方最关心的，因为它直接对应"多少用户请求被网关吃掉了"。三个指标都从网关自己上报，采样间隔 10 秒。

## 5. 灰度路由

灰度按请求头里的 `X-Gray-Tag` 路由，没有这个头的请求走稳定版本。灰度比例的推进节奏是固定的四档：5% → 20% → 50% → 100%，每一档至少观察 30 分钟才允许推进下一档。观察期内如果错误率相对基线上升超过 0.5 个百分点，自动回退到上一档并通知发布人。

灰度标记的分配用的是 `user_id` 的哈希取模，不是随机数。用哈希是为了让同一个用户在整个灰度期间稳定落在同一侧，否则用户会看到功能时有时无。这条约定和发布规范里的灰度要求是同一件事，两份文档如果对不上，以发布规范为准。

## 6. 不放进网关的东西

有两类需求反复被提出、也反复被拒绝，记在这里省得每次重新讨论。

第一类是"在网关做业务级的参数校验"。提出的理由通常是"这样后端就不用校验了"。拒绝的理由：网关拿不到业务的完整上下文，只能做格式校验，而格式校验放在网关会让网关跟着业务频繁发版；更关键的是后端不能依赖上游的校验，它必须自己校验一遍，所以网关那一遍是纯粹的重复。

第二类是"在网关做结果缓存"。提出的理由是减少下游压力。拒绝的理由：缓存的失效逻辑必然和业务语义绑定，网关一旦持有业务缓存就等于持有业务状态，与"网关无状态"这条基本约定冲突。需要缓存的场景应该在下游服务自己做，或者走独立的缓存服务。

## 7. 联系人与值班

网关的值班按周轮换，交接时间是周二上午 10:30，与发布窗口错开半天。值班期间需要盯的看板有三个：限流拒绝量、熔断打开次数、鉴权失败率。鉴权失败率突然上升通常意味着某个调用方的密钥轮换出了问题，这类问题优先级最高，因为它会让整个调用方的流量全挂。

紧急联系方式在内部通讯录，不在本文档维护。涉及跨机房的限流配额调整需要两个人确认，单人无法生效，这是配置中心里配的强制审批规则。
