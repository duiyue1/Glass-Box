# 订单平台测试方案

本文用于测试 Glass-Box 的测试方案检索、验收标准抽取、数字和状态枚举识别，以及与订单架构和接口契约的关系提取。

## 1. 测试范围

测试对象包括 `order-api`、`inventory-service`、`payment-service`、`fulfillment-service`、Kafka 事件链路和 PostgreSQL outbox。测试不覆盖第三方支付网关内部实现，但覆盖网关超时、重复通知、签名错误和未知结果。

测试环境使用独立 Kafka 集群、PostgreSQL 16 和 Redis 7。测试数据每天清理一次，订单号前缀为 `test_`。严禁使用真实用户、真实银行卡号或生产 topic。

## 2. 验收门槛

发布前必须满足：

- 单元测试通过率 100%；
- 集成测试通过率 100%；
- 关键端到端场景通过率 100%；
- 订单 API P99 小于 180 ms；
- 消息重复消费不产生重复扣款和重复发货；
- 订单状态非法迁移数为 0；
- 高优先级缺陷为 0；
- 中优先级缺陷不超过 3 个且有明确豁免人。

## 3. 测试数据

|数据集|数量|用途|
|-|-|-|
|正常商品|1000 个 SKU|基础下单和库存预占|
|低库存商品|50 个 SKU|并发预占冲突|
|下架商品|100 个 SKU|商品校验失败|
|大订单|每单 50 个 SKU|边界性能|
|重复请求|每组 10 次|幂等性|
|异常金额|每组 20 个|金额和精度校验|

金额数据使用整数分。测试 `0`、`1`、`99999999999999` 和 `100000000000000` 分，确认超过最大值时拒绝。不要用浮点数构造金额断言。

## 4. API 测试

### 4.1 创建订单

|用例|步骤|预期|
|-|-|-|
|正常创建|提交 2 个有效 SKU|返回 202，状态 CREATED，生成唯一 order_id|
|空商品|items=[]|返回 40001，不写入订单和 outbox|
|数量为 0|quantity=0|返回 40001|
|数量超过 999|quantity=1000|返回 40001|
|重复 key|相同 Idempotency-Key 连续请求 10 次|只创建 1 个订单，所有成功响应结果一致|
|不同请求复用 key|相同 key 但 items 不同|返回幂等冲突，不创建第二订单|
|金额溢出|金额超过上限|返回 40001，不进入支付流程|

### 4.2 取消订单

|用例|初始状态|预期|
|-|-|-|
|创建后取消|CREATED|状态变为 CANCELLED，库存无预占|
|支付中取消|PAYMENT_PENDING|取消成功或返回处理中，不产生新支付请求|
|已支付取消|PAID|返回 ORDER_STATE_CONFLICT，必须走退款|
|重复取消|CANCELLED|返回当前结果，不产生第二次状态迁移|
|并发取消和支付|PAYMENT_PENDING|最终只能进入 PAID 或 CANCELLED 之一|

## 5. 事件测试

### 5.1 重复和乱序

1. 发布同一个 `event_id` 两次，确认消费者只执行业务变更一次；
2. 先发布 `PAYMENT_SUCCEEDED`，再发布 `INVENTORY_RESERVED`，确认后者不能把状态回退；
3. 发布未知 `schema_version=99`，确认进入死信并触发告警；
4. 发送缺少 `order_id` 的事件，确认校验失败且不提交业务变更；
5. 重启消费者后重复拉取未提交 offset 的消息，确认幂等表阻止重复处理。

### 5.2 Outbox

- 订单事务回滚时不能出现 outbox 记录；
- 订单事务成功但 relay 进程立即退出时，重新启动后必须继续发布；
- Kafka 暂不可用时 outbox 数量增长但订单 API 仍能在 2 秒内返回；
- 同一 outbox 事件最多被重复发布 3 次，消费者仍只能处理一次；
- `published_at` 写入失败时不能把事件误标记为已发布。

## 6. 支付异常测试

支付网关返回成功：订单进入 PAID。

支付网关返回失败：订单进入 PAYMENT_FAILED，并释放库存预占。

支付网关连接超时：订单保持 PAYMENT_PENDING，支付状态为 UNKNOWN，不能创建第二个 payment_request_id。

支付成功通知重复到达：第一次通知完成扣款确认，后续通知只记录重复事件。

支付通知签名错误：拒绝处理，记录 request_id，不改变订单状态。

支付查询接口返回“处理中”：继续保持 PAYMENT_PENDING，最多轮询 12 次，每次间隔 5 秒；超过轮询上限后转人工处理队列。

## 7. 并发和性能测试

使用 200、500、1000 并发用户分别压测 10 分钟。每个用户随机选择 1 到 5 个 SKU，低库存商品占比 10%。记录：

- API P50/P95/P99；
- 数据库连接池等待时间；
- Kafka producer latency；
- consumer lag；
- 状态迁移冲突率；
- 重复消费率；
- outbox pending 数量。

性能通过条件：1000 并发时创建订单 P99 小于 180 ms，错误率小于 0.1%，consumer lag 在测试结束后 3 分钟内恢复到 1000 以下。

## 8. 故障注入

|故障|注入方式|预期恢复|
|-|-|-|
|PostgreSQL 主库不可用|阻断连接 60 秒|API 返回可识别错误，恢复后不丢订单|
|Kafka 不可用|停止 broker 2 分钟|订单进入 outbox，Kafka 恢复后继续发布|
|库存服务延迟|响应延迟 8 秒|order-api 不被同步阻塞|
|支付网关超时|随机 20% 请求超时|状态进入 UNKNOWN，不能重复扣款|
|消费者进程退出|处理 50 条消息时 kill|重启后从未提交 offset 继续|
|时钟偏移|容器时间偏移 30 秒|事件排序使用 occurred_at 与接收时间双字段|

详细处置顺序见《测试-订单平台事故复盘与运行手册》。

## 9. 回归清单

每次修改订单状态机、幂等键、事件 schema、重试策略或 outbox relay 时必须执行：

- 创建订单全量 API 用例；
- 重复请求 10 次；
- 状态迁移矩阵；
- 乱序事件；
- 重复支付通知；
- Kafka 不可用；
- 数据库事务回滚；
- 死信重放；
- 版本兼容性；
- 监控指标和告警规则。

任何一项失败都不能只修改测试断言绕过，必须确认架构和接口契约是否同时需要更新。
