# 订单平台事故复盘与运行手册

本文用于测试事故复盘、运行手册、告警阈值、时间序列、操作步骤和与架构/测试文档的交叉检索。

## 1. 事故摘要

2026-08-18 10:20 至 10:47，订单平台出现支付成功但订单状态长时间停留在 `PAYMENT_PENDING` 的问题。影响区域是支付事件消费者 `payment-confirmation-consumer`，峰值约 4200 个订单延迟确认，未发现重复扣款。

根因是消费者发布版本时将 Kafka consumer group 从 `payment-confirmation-v1` 错误改为 `payment-confirmation-v2`，新 group 没有从旧 group 的 committed offset 接续，而是从 `latest` 开始消费。发布期间产生的 4200 条事件没有被新 group 读取。

## 2. 影响与判断

用户侧表现：

- 支付页面显示成功，但订单详情仍是 PAYMENT_PENDING；
- 部分用户重复点击查询，没有造成重复支付；
- 履约服务未收到 PAID 事件，因此没有错误发货；
- 对账任务在第二天发现支付平台和订单库存在暂时性不一致。

明确未发生的影响：

- 没有重复扣款；
- 没有错误发货；
- 没有订单数据丢失；
- outbox 没有丢消息；
- payment_request_id 幂等约束仍然有效。

## 3. 时间线

|时间|事件|
|-|-|
|10:15|开始发布 payment-service v2.8.0|
|10:20|新 consumer group 变为 Ready|
|10:22|PAYMENT_PENDING 数量超过 1000|
|10:24|监控触发 payment confirmation lag 告警|
|10:27|值班工程师确认支付平台成功数与订单 PAID 数不一致|
|10:31|发现 v2 group committed offset 从最新位置开始|
|10:34|停止 v2 consumer，恢复 v1 group|
|10:39|积压事件开始下降|
|10:47|积压恢复到 100 以下，进入观察|
|11:20|4200 个订单全部确认|
|次日 09:00|完成支付平台对账，确认无重复扣款|

## 4. 立即处置

当 `PAYMENT_PENDING` 超过 1000 且持续 5 分钟时：

1. 暂停继续发布 payment-service；
2. 查看 Kafka topic `payment.events` 的各 consumer group lag；
3. 对比支付平台成功数、订单 `PAID` 数和 `PAYMENT_PENDING` 数；
4. 确认 `payment_request_id` 是否出现重复；
5. 如果发现新 group 从 latest 消费，停止新 group；
6. 恢复正确 group，使用已经提交的 offset 继续消费；
7. 观察 lag 是否每分钟下降；
8. 对订单表和支付平台做抽样对账；
9. 记录恢复开始和结束时间。

不要直接批量把订单状态从 PAYMENT_PENDING 改成 PAID。支付状态必须以支付平台确认结果和事件幂等处理为依据。

## 5. 常用检查命令

```bash
kafka-consumer-groups \\
  --bootstrap-server kafka.prod:9092 \\
  --describe \\
  --group payment-confirmation-v1
```

```sql
SELECT status, COUNT(*)
FROM orders
WHERE updated_at >= '2026-08-18 10:00:00'
GROUP BY status;
```

```sql
SELECT payment_request_id, COUNT(*) AS n
FROM payments
WHERE created_at >= '2026-08-18 10:00:00'
GROUP BY payment_request_id
HAVING COUNT(*) > 1;
```

检查时区必须统一使用 UTC。不要把本地时间直接拼到 SQL 查询里，否则可能漏掉事故窗口前后各 8 小时的数据。

## 6. 恢复后验证

恢复后必须完成以下验证：

- lag 降至 1000 以下并持续 10 分钟；
- `PAYMENT_PENDING` 数量回到基线；
- 支付平台成功数与订单 PAID 数差异小于 0.1%；
- 重复 `payment_request_id` 数量为 0；
- 死信 topic 没有新增异常；
- fulfillment-service 收到的 PAID 事件数量和订单状态一致；
- 订单 API P99 没有超过 180 ms；
- 对账抽样至少 200 个订单，全部能关联到唯一支付记录。

## 7. 长期修复

### 7.1 发布检查

发布脚本必须阻止 consumer group 名称变化，除非变更单明确包含 offset 迁移方案。部署前检查：

```text
old_group == new_group
或
存在经过审核的 offset migration plan
```

### 7.2 监控增强

新增三类告警：

- payment confirmation lag > 1000 持续 5 分钟；
- 支付成功数 - PAID 数 > 200；
- 新 consumer group 在没有迁移记录时出现。

### 7.3 测试增强

测试方案新增：

- consumer group 变更回归；
- committed offset 恢复；
- 从 earliest/latest 启动的差异；
- 发布中消费者重启；
- 事件积压恢复时间；
- 对账任务一致性检查。

相关测试项见《测试-订单平台测试方案》，架构约束见《测试-事件驱动订单平台架构设计》。

## 8. 值班交接

交接必须包含：

- 当前 payment.events lag；
- PAYMENT_PENDING 数量；
- 最近一次部署版本和 consumer group；
- 死信数量；
- 最近一次支付对账时间；
- 是否有正在进行的 offset 操作；
- 未关闭的 P1/P2 告警。

禁止只写“系统正常”。必须给出数值和时间，否则下一班无法判断基线是否变化。
