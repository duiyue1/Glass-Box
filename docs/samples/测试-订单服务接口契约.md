# 订单服务接口契约

本文用于测试 API 参数检索、表格切块、代码块保留、数字溯源和与《测试-事件驱动订单平台架构设计》《测试-订单平台测试方案》的交叉引用。

## 1. 创建订单

```http
POST /api/v1/orders
Content-Type: application/json
Idempotency-Key: 20260823-user-1001-001
```

请求体：

```json
{
  "user_id": 1001,
  "items": [
    {"sku_id": "SKU-RED-001", "quantity": 2}
  ],
  "shipping_address_id": "addr-7788",
  "coupon_code": "SUMMER2026"
}
```

参数约束：

|字段|类型|必填|约束|
|-|-|-|-|
|user_id|integer|是|大于 0|
|items|array|是|1 到 50 个元素|
|sku_id|string|是|长度 1 到 64|
|quantity|integer|是|1 到 999|
|shipping_address_id|string|是|长度 1 到 128|
|coupon_code|string|否|长度不超过 64|

成功响应为 `202 Accepted`，表示订单已经写入订单库和 outbox，但库存、支付和履约仍然异步处理。

```json
{
  "order_id": "ord_20260823_000001",
  "status": "CREATED",
  "event_id": "evt_7f21",
  "created_at": "2026-08-23T10:20:30Z"
}
```

客户端不能因为收到 `202` 就认为订单已经支付成功。需要通过查询接口或订单事件订阅观察状态变化。

## 2. 查询订单

```http
GET /api/v1/orders/{order_id}
Authorization: Bearer <token>
```

成功响应：

```json
{
  "order_id": "ord_20260823_000001",
  "user_id": 1001,
  "status": "PAYMENT_PENDING",
  "version": 3,
  "total_amount": 19900,
  "currency": "CNY",
  "items": [
    {"sku_id": "SKU-RED-001", "quantity": 2, "unit_amount": 9950}
  ],
  "updated_at": "2026-08-23T10:21:08Z"
}
```

`total_amount` 和 `unit_amount` 的单位是分。接口不会返回浮点金额。订单不存在返回 `40401`，无权限返回 `40301`，查询参数非法返回 `40001`。

## 3. 取消订单

```http
POST /api/v1/orders/{order_id}/cancel
Idempotency-Key: cancel-ord_20260823_000001-01
```

只有 `CREATED` 和 `PAYMENT_PENDING` 状态允许取消。已经 `PAID` 的订单必须走退款流程，不能调用取消接口。重复取消同一订单时，如果第一次已经成功，第二次返回 `200` 并携带当前状态；如果第一次仍在处理中，返回 `202`。

## 4. 查询支付状态

```http
GET /api/v1/orders/{order_id}/payment
```

支付状态枚举：

```text
NOT_STARTED
PENDING
SUCCEEDED
FAILED
UNKNOWN
REFUNDED
```

`UNKNOWN` 不是失败。支付网关超时后，系统无法确认结果时必须返回 `UNKNOWN`，客户端不得自动发起第二个支付请求。需要等待异步通知或调用支付查询任务。

## 5. 错误格式

所有业务错误使用统一结构：

```json
{
  "error": {
    "code": "ORDER_STATE_CONFLICT",
    "message": "订单当前状态不允许取消",
    "request_id": "req_2f7a",
    "retryable": false,
    "details": {
      "current_status": "PAID"
    }
  }
}
```

错误码规范：

|错误码|HTTP|可重试|含义|
|-|-|-|-|
|REQUEST_INVALID|400|否|请求字段不合法|
|UNAUTHORIZED|401|否|认证失败|
|ORDER_NOT_FOUND|404|否|订单不存在|
|ORDER_STATE_CONFLICT|409|否|状态不允许当前操作|
|RATE_LIMITED|429|是|超过限流|
|DEPENDENCY_TIMEOUT|504|是|下游超时|
|INTERNAL_ERROR|500|视情况|服务内部错误|

## 6. 幂等要求

所有会改变订单状态的接口都必须携带 `Idempotency-Key`。Key 长度为 8 到 128 个 ASCII 字符，同一用户下 24 小时内不能复用同一 key 执行不同请求。

如果请求第一次执行成功但响应丢失，客户端使用同一个 key 重试，服务返回第一次执行结果。不能每次重试生成新的 key，否则无法阻止重复下单。

## 7. 限流和超时

默认限流：每个用户创建订单每分钟 30 次，每个 IP 查询订单每分钟 600 次。创建订单上游超时为 2 秒，查询订单超时为 500 ms，取消订单超时为 1 秒。

超过限流返回 `429` 和 `Retry-After`，单位为秒。客户端应使用指数退避，不得在 100 ms 内连续重试超过 3 次。

## 8. 兼容性与版本

当前路径为 `/api/v1`。新增字段只允许向后兼容；删除字段或改变枚举含义必须发布 `/api/v2`。事件 schema 和 HTTP 响应不是同一个版本体系，不能因为 HTTP API 仍是 v1 就假设 Kafka 事件也是 v1。

接口状态迁移和事件关系见《测试-事件驱动订单平台架构设计》。测试用例和验收标准见《测试-订单平台测试方案》。线上异常处理见《测试-订单平台事故复盘与运行手册》。
