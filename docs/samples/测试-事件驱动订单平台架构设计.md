# 事件驱动订单平台架构设计

本文用于测试 Glass-Box 资料库的长文档切块、wiki 编译、来源溯源、跨文档链接和图谱关系。相关文档包括《测试-订单服务接口契约》《测试-订单平台测试方案》《测试-订单平台事故复盘与运行手册》。

## 1. 背景与目标

订单平台负责接收用户下单请求，完成库存预占、支付确认、订单落库和履约通知。平台采用事件驱动架构，核心目标是将下单接口的同步响应时间控制在 P99 180 ms 以内，同时保证订单状态最终一致、重复消息不造成重复扣款或重复发货。

本次设计覆盖四个核心服务：`order-api`、`inventory-service`、`payment-service`、`fulfillment-service`。服务之间通过 `order.events`、`payment.events` 和 `fulfillment.events` 三个 Kafka topic 通信。所有事件必须包含 `event_id`、`order_id`、`event_type`、`occurred_at` 和 `schema_version`。

## 2. 总体架构

```text
Client
  |
  v
order-api ---> PostgreSQL(order)
  |
  +---------> Kafka: order.events
                 |
        +--------+---------+
        v                  v
 inventory-service    payment-service
        |                  |
        +--------+---------+
                 v
        fulfillment-service
                 |
                 v
          notification-service
```

`order-api` 只负责请求校验、订单初始状态写入和事件发布，不直接调用库存、支付或履约服务。这样做的原因是避免同步调用链过长，也避免一个下游超时阻塞用户下单。

事件发布采用 outbox 模式。订单事务提交时同时写入 `order_outbox`，后台 relay 每 500 ms 扫描一次未发布事件，将事件发送到 Kafka，成功后写入 `published_at`。relay 允许重复发送，因此消费者必须实现幂等。

## 3. 状态机

订单状态如下：

```text
CREATED -> INVENTORY_RESERVED -> PAYMENT_PENDING -> PAID -> FULFILLING -> COMPLETED
    |              |                    |
    v              v                    v
  CANCELLED     CANCELLED            PAYMENT_FAILED
```

状态迁移必须满足以下约束：

| 当前状态 | 目标状态 | 触发方 | 允许条件 |
|-|-|-|-|
| CREATED | INVENTORY_RESERVED | inventory-service | 库存预占成功 |
| CREATED | CANCELLED | order-api | 用户主动取消且未进入支付 |
| INVENTORY_RESERVED | PAYMENT_PENDING | order-api | 库存事件已确认 |
| PAYMENT_PENDING | PAID | payment-service | 支付网关返回成功 |
| PAYMENT_PENDING | PAYMENT_FAILED | payment-service | 支付失败或超时 |
| PAID | FULFILLING | fulfillment-service | 支付成功事件已消费 |
| FULFILLING | COMPLETED | fulfillment-service | 发货单创建成功 |

任何服务都不能直接把订单改成 `COMPLETED`。状态更新使用 compare-and-set，条件中必须带上当前版本号 `version`，防止乱序事件覆盖新状态。

## 4. 幂等和一致性

每个消费者维护 `event_consumed` 表，主键为 `consumer_name + event_id`。处理消息时先插入消费记录，再执行业务变更；如果插入主键冲突，说明消息已经处理过，直接提交 offset。

支付服务额外使用 `payment_request_id` 做幂等键。支付网关请求超时后不能直接重试未知结果，必须先调用查询接口确认原请求状态。只有确认不存在支付记录时才允许创建新支付请求。

库存预占使用 `reservation_id`，格式为 `order_id:sku_id`。同一订单同一 SKU 不允许存在两个有效预占。预占超时时间为 15 分钟，过期释放任务每 30 秒运行一次，每次最多处理 1000 条记录。

## 5. 可靠性设计

Kafka producer 开启 `acks=all`，重试次数为 8，单次发送超时 3 秒。消费者批量大小为 100，最大 poll 间隔为 5 秒。消费失败时使用重试 topic，不在主 topic 上长时间阻塞其他订单。

重试次数和退避如下：

|次数|等待|处理|
|-|-|-|
|1|10 秒|重试原处理器|
|2|30 秒|重试原处理器|
|3|2 分钟|重试原处理器|
|4|10 分钟|写入死信 topic|

死信 topic 保留 14 天。死信重新处理必须使用新的 `replay_id`，不能复用原始 `event_id`，但业务幂等键保持不变。更多异常处理见《测试-订单平台事故复盘与运行手册》。

## 6. 数据模型

订单表 `orders` 关键字段：

```sql
id              bigint primary key
user_id         bigint not null
status          varchar(32) not null
version         bigint not null default 0
total_amount    decimal(18,2) not null
created_at      timestamp not null
updated_at      timestamp not null
```

outbox 表 `order_outbox` 关键字段：

```sql
id              bigint primary key
event_id        varchar(64) unique not null
aggregate_id    bigint not null
event_type      varchar(64) not null
payload         jsonb not null
published_at    timestamp null
created_at      timestamp not null
```

金额统一使用分为单位的整数计算，接口层可以展示为元，但数据库和事件中不允许使用浮点数。金额最大值为 999999999999.99 元，超过该值应在请求校验阶段拒绝。

## 7. 可观测性

必须记录以下指标：

- `order_api_request_latency_ms`：按接口和状态码统计 P50/P95/P99；
- `order_outbox_pending_total`：未发布 outbox 数量；
- `kafka_consumer_lag`：每个 topic、partition 的消费延迟；
- `payment_unknown_result_total`：支付请求超时但结果未知的数量；
- `order_state_transition_failure_total`：非法状态迁移数量；
- `dead_letter_total`：死信数量。

告警规则：

|指标|阈值|持续时间|级别|
|-|-|-|-|
|接口 P99|> 180 ms|10 分钟|P1|
|outbox 未发布|> 5000|5 分钟|P1|
|消费 lag|> 100000|5 分钟|P1|
|死信新增|> 100/分钟|3 分钟|P2|
|非法状态迁移|> 10/分钟|5 分钟|P2|

## 8. 灰度与回滚

新事件版本先以 `schema_version=2` 灰度发布。消费者必须兼容 `schema_version=1` 和 `schema_version=2` 至少 14 天。灰度期间按 `user_id % 100` 选择 5% 用户，观察 P99、死信和状态迁移失败率。

回滚顺序：

1. 停止扩大灰度比例；
2. 回滚 producer，使其只发布 v1；
3. 保留消费者双版本解析；
4. 处理灰度期间积压消息；
5. 确认 outbox 和死信数量恢复正常；
6. 最后再回滚消费者。

不允许先回滚消费者再回滚 producer，否则 v2 事件可能无法解析。接口字段和状态码契约见《测试-订单服务接口契约》，验证项见《测试-订单平台测试方案》。
